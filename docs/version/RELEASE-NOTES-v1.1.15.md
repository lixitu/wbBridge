## 本版主题

这一轮有四批内容，其中**唯一的新功能是 WB · auto**：对外多一个合成模型名，请求打给它时由本工具在**当前可用**的免费模型里选一个真实模型，并按请求内容避开「不能看图」「不能调工具」的模型。其余三批（审查修复、并发 4→8、面板无障碍）都是不带新功能的收口。

v1.1.15 在同一能力上补了两件事：**这个名字统一成 `WB · auto`**（不再有 `WB.auto` 写法），以及**它被写进 WorkBuddy / CodeBuddy 的模型配置**——后者是对 v1.1.14 里「绝不写进插件」那条裁定的撤销，因为「插件里看不到，就没人知道怎么用」。

WB · auto 的失败处理值得单独说明：用户要求「使用过程中出现受限、超时、不可用时，同时从可用模型中移除，并更新模型列表中该模型的状态」——实读代码后的结论是**这三件事全部由既有链路承担，本轮没有新增任何摘除或状态代码**。需要新增的只有一个不变量：**记账键必须是实际选中模型的全限定 id**，否则「摘除」会打在 `"WB · auto"` 这个并不存在的假键上，真实模型留在通过集里被反复选中。

## 新增：WB · auto 智能路由（v1.1.14 ~ v1.1.15）

1. **`GET /v1/models` 多一个入口**：可用池非空时，列表**末尾**追加一条 `{ "id": "WB · auto", "object": "model", "owned_by": "opencode", "name": "WB · auto" }`。池为空时**不追加**——不给客户端一个「点了必失败」的入口。
2. **`POST /v1/chat/completions` 接受 `model = "WB · auto"`**（v1.1.15 起这是**唯一**被接受的名字；此前写作 `WB.auto`，因为 1.1.11~1.1.14 从未构建、从未打标签，改名不影响任何已交付的二进制），由本工具在同一份池快照里选一个实际模型。分级规则：
   - 请求带图片 → 只从声明支持图片的模型里选；
   - 请求带工具定义 → 排除「仅对话」模型，且要求支持函数调用；
   - 两者都有 → 两个条件都要满足；
   - 纯文本 → 整个可用池。
   - 某一级候选为空时**退回全池**，随后由既有的模型校验给出 400（不静默换一条不合规的通道）。
3. **响应里的 `model` 字段是实际模型的全限定 id**（例如 `modelscope/Qwen/Qwen3-8B`），不是 `WB · auto`；用量统计、逐模型状态、「已校验」集合也都记在这个真实 id 上。所以用量页**不会**出现「WB · auto」这一行——它不是模型，是一把路由。
4. **失败即移出可用集合**（复用既有判决）：真实请求里该模型报错（受限 / 超时 / 不可用）时，它被从「已校验」集合摘掉，同一批状态写入重算可用模型数并更新该模型在列表里的状态，面板行随即变化。**四类格式性失败**（输出截断、信封格式、原生工具越权、工具调用格式）**不摘除**——那是请求形态问题，不是模型坏了。
5. **四种情况不改变任何模型状态**，如实列出以免误解：客户端中途取消、超过并发上限的 429、请求体读取超时（408）、模型校验的本地 400。它们都在记账之前结束。
6. **被摘除的模型不会自动回到列表**：摘除当次只影响 `/v1/models`、`status.json` 与面板；插件的 `models.json` 要等下一轮同步才收敛，恢复某模型要靠「重新检测」或「刷新」。
7. **（v1.1.15 起的改动）`WB · auto` 会写进 WorkBuddy / CodeBuddy 的 `models.json`**，排在本工具名下的逐模型条目之后。v1.1.14 裁定的是「绝不写进插件」，用户实测后推翻了这个决定——插件里看不到这个名字，就等于没人知道怎么用。写入形态（**保守声明**，能力字段一律宁少勿多）：
   - `id` / `name` 都是 `WB · auto`；这个 `id` 直接是插件发送请求时填进 `model` 的值，服务端按第 2 条改写，所以插件侧不需要知道任何真实模型 id。
   - `supportsToolCall` **不是固定值**，取「可用池里是否存在能接工具调用的候选」。⚠ 这一条比维护者选定的「保守声明」更收紧了一步：发布集里只有「仅对话」模型时如果声明 `true`，插件侧的工具请求会恒定落到退化档再被模型校验拒成 400——所以让插件侧声明与核心选档共用同一个能力谓词，两者不可能分叉。
   - `supportsImages` 固定 `false`；`maxInputTokens` 取池内**最小**上下文（每次同步重算，池里一个数值都没有就不写这个键）；不写 `reasoning`、不写 `maxOutputTokens`。
   - **只在发布集非空时写**：模型列表为空就不写这一条，不给插件一个「选了必失败」的入口。
   - `sync.count` 与 `status.json` 里的 `sync.targets.<目标>.count` **仍然只数真实模型**，这条合成路由不计入——面板不会出现一行「WB · auto」。
   - 若用户自己手动建了同名 `id` 的条目，按既有铁律**不覆盖**，本工具直接放弃写这一条。
   - 🔴 插件侧能不能识别并按这条路由正常发请求，**从未实测**（见「未验证」）。
8. 接入边界**一字未放宽**：仅回环监听、所有路由都要 Bearer 鉴权、任何非空 `Origin` → 403、并发 ≤8、请求体 ≤8MB。所以 CLI / 桌面 agent 直连 `127.0.0.1:<port>` 可用，浏览器内嵌 `fetch` 仍然不行。
9. **两条刻意没做的取舍**（避免「顺手扩大范围」）：同一请求内**不换模型重试**（一次请求只打一个模型，失败由客户端自己决定重发）；对话请求**不加整体超时预算**——因此「上游挂死且客户端不取消」这一种情况既不失败也不摘除，这个缺口如实保留。

## 修复与改进（v1.1.11 ~ v1.1.13 批次，本版一并带上）

### 核心

1. **客户端断开后不再泄漏在途会话与权限轮询任务**：一次对话生成期间，核心除了转发内容，还会**每 250ms 轮询**该会话的原生工具待审批状态。原先清理逻辑写在生成函数的「正常结束 / 出错」路径上——而 hyper 在客户端断开时是**直接丢弃整个请求处理任务**，那条清理路径一行都不会执行。后果是每次断开发一个永不结束的轮询任务，并在状态表里留下一条会话记录（含 `usage_by_session`、待审批条目），活动流也停不掉。现改为**对象销毁即清理**的守卫：无论任务是正常返回、报错返回，还是被运行时丢弃，清理都会执行且只执行一次。
2. **`/admin/*` 的请求体读取纳入与对话接口同一份 20 秒预算**：原先这份预算只挂在 `/v1/chat/completions` 外面那一层，五个管理入口（探测、代理开关、导入、刷新、三条平台 Key 动作）都没有它。管理路由不受对话接口的并发上限限制，因此一个只发头不发体的连接可以**无限期占住**该请求的任务与缓冲。
3. **OpenCode 会话响应缺少会话 id 时当场失败，不再退化成空串**：原先取不到 id 会以空字符串继续，而**空串是一把会被共享的键**——两个并发请求会在会话状态表与用量表里落到同一个条目上互相干扰，删除路径也会退化成 `/session/`。

### 面板

4. **两处颜色的对比度达标**（数值由 `src/styles/variables.css` 的 token 实算，不是目测）：`--orange` 浅色 `#bc752c` → **`#a4581a`**（兼作 13px 错误正文，原先 3.5:1 低于正文要求的 4.5:1；暗色已达标未动）；`--switch-off` `#aab2ae` → **`#7f8a86`**（可交互控件按 WCAG 1.4.11 需 ≥3:1）。
5. **十处小字号说明文字改用 `--muted-strong`**：副标题、页脚、模型行耗时、空列表提示、指标条说明、详情栏引导语、平台页 id / 申请页网址 / 提示、关于页版本说明。**刻意没改**：指标条「空闲」（22px 大字号）、侧栏导航色底（装饰性）。
6. **`Esc` 不再从输入框里抢走「收起详情」**：输入框、文本域、可编辑元素内的 Esc 一律放行。
7. **平台视图「读取免费模型（重新应用）」的成功提示真正会显示并自动消隐**；切走该视图时清掉待触发的消隐定时器。
8. **忙态按「就是这个动作在飞」判定**：状态条「重试」与集成页「导入」不再被任何动作点亮，并补 `aria-busy`。
9. **空模型列表不再声明为列表角色**：`role="listbox"` 只在列表非空时挂。

### 容量（v1.1.13，2026-10-10 用户裁定）

10. **对话接口并发上限 4 → 8**：`MAX_CONCURRENT_REQUESTS` 由 4 调到 8，为本工具「服务一切 OpenAI 兼容客户端」的定位让路。**对外契约有一处字面变化**：超限的 429 文案由 `At most four requests may run at once` 改为 `At most eight requests may run at once`（`code`/`type`/状态码逐字不变）。上限值由 `red_lines.rs` 固定断言钉死。

## 未验证（不得伪装）

- 🔴 **WB · auto 一次真实请求都没发过**：316 项测试全部跑在**注入的假后端**上（可控地成功 / 失败 / 挂住）。真实模型池里的实际分散度、图片请求真的被路由到支持视觉的模型、失败一次之后该模型确实从列表与 `/v1/models` 消失、以及 WorkBuddy/CodeBuddy 侧对多出来这个名字的反应——**都没在真实环境跑过**。
- 🔴 **v1.1.15 写入插件配置只验证到临时目录沙箱**：合成条目落盘、被该文档的可用列表列出、下一轮空同步删干净，全在 `mkdtemp` 的假插件目录里跑过。**WorkBuddy / CodeBuddy 自身能不能认出这条 `WB · auto`、能不能按它发出请求**（插件对条目字段的要求、是否自行规范化模型名）完全未知——本工具只按自己既有的 `models.json` 约定写，那套约定对逐模型条目成立，对合成条目是**推定**成立。
- 🔴 **`maxInputTokens` 取池内最小值**是最保守的选法，代价如实记录：池里同时有 8K 与 128K 上下文的模型时，插件侧会按 8K 提前截断，可能浪费长上下文模型的容量。没有实测过这种混搭池里的真实表现。
- 🔴 **摘除与恢复的端到端**：「恢复只能靠重新检测/refresh」是按读码得出的结论，没实测过一整轮「失败 → 消失 → 重新检测 → 回来」。
- 🔴 **GUI 实机一次都没有**：面板改动与 WB · auto 的列表展示都只有构建与静态检查通过作证据。
- 🔴 **断连清理的修复效果**：修复前后残留任务数的对比未实测。
- 🔴 **管理接口的 20s 预算**：真实半开发连接的行为未实测。
- 🔴 **8 路并发的真实表现**：没有在真实 OpenCode + 真实多 agent 负载下压过；调到 8 只是放开本工具自己的闸门，不代表上游扛得住。
- 🔴 **1.1.11 ~ 1.1.15 都未构建、未打标签**：期间并行轮次一度推进到 `1.2.0`，已按维护者裁定回退——`1.2.x~1.3.x` 从未构建、从未打标签，**不得再占用**。这也是 v1.1.15 敢把合成模型名从 `WB.auto` 全局改成 `WB · auto` 的唯一前提：没有任何已交付二进制带过旧名字。发布（提交 → 在含版本推进的提交上打 `v1.1.15` → CI → Publish）属维护者操作。
