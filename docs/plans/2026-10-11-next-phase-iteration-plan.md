## 一、项目现状全景盘点（Phase 1）

### 1.1 产品定位与架构

WB Bridge 是一个 Tauri 2 跨平台托盘应用，把 OpenCode 的免费模型通过**隔离的 OpenCode 运行时**供给 WorkBuddy / CodeBuddy 使用。当前三层架构：

| 层 | 形态 | 关键落点 |
|---|---|---|
| 核心 Core | Rust crate `wbbridge-core`，**静态链接**进壳（2026-10-01 完成 Node sidecar 迁移） | `src-tauri/core/src/`（18 个模块，8.7 万行量级） |
| 壳 Shell | Tauri 2，管理窗口 / 托盘 / 核心生命周期 | `src-tauri/src/lib.rs`（45KB） |
| 面板 Panel | Vue 3 + Vite，本地回环 HTTP 经 Tauri 命令与核心通信 | `src/`（12 个视图 + 4 个 JS 内核模块） |

### 2.3 核心缺陷：记账键双形态并存，导致「失败即摘除」完全落空

这是本次盘点挖出的**唯一 P0**，也是 v1.1.14 明确声称已用决策点 D2 防住的场景。

**证据（`status.json` 实读）：**

```
modelResults["opencode/space-bunny-free"]   = { ok: true,  source: "probe",   time: "2026-10-10T15:48:53" }
modelResults["OC · Space Bunny Free"]       = { ok: false, status: 502, source: "request", time: "2026-10-10T01:00:04" }
usage.models["OC · Space Bunny Free"]       = { requests: 2, ok: 0, failed: 2, avgMs: 64635 }
availableModels 含 "opencode/space-bunny-free"  → true   ← 打了 2 次失败仍在发布！
```

**根因链：**

1. `prepare()` 允许两种匹配：`strict_eq(model.id, body_model)` **或** `client_model_id(model) == candidate`（`protocol.rs:181-186`）——即全限定 id 与显示名 `OC · Space Bunny Free` **都能命中同一个模型**。
2. `server.rs:941` 的记账键取 `body["model"]` **原值**。客户端（插件）按 `models.json` 里的显示名发请求 ⇒ 记账键 = 显示名。
3. `auto.rs` 已把 `WB · auto` 改写成全限定 id（D2 做对了），但**手动指定模型这条路没做同款归一化**。
4. 探测路径 `orchestration.rs:1153` 用 `model_id`（全限定 id）记账 ⇒ 同一个模型在 `modelResults` 里出现**两个互斥的键**。
5. `record()` 的 `validated.remove(model)` 删的是显示名键；而 `usable_models()` 用全限定 id 判定 ⇒ **删除打空**，坏模型永久停留在可用池。

**影响面：** 42 个记账键中 3 个是显示名形态（7.1%），`usage.models` 12 个键里同样有 3 个。这不是边缘 Case——它精确命中了用户提 WB · auto 需求时的原话「在使用过程中出现受限、超时、不可用时，同时从可用模型中移除」。

**为什么 v1.1.15 的 316 项测试没抓到：** 全部跑在**注入的假后端**上，客户端总是直接发全限定 id。真实插件按显示名发请求这条路径从未被测到——这是一个典型的「测试替身替掉了一半真相」的案例。

## 三、候选需求池（Phase 3）

每条候选需求含十要素：编号 / 名称 / 问题陈述 / 证据 / 目标 / 范围 / 方案要点 / 依赖 / 风险 / 验收信号。

### 3.1 【R-01】修复记账键双形态，让「失败即摘除」真正生效 🔴 P0

| 要素 | 内容 |
|---|---|
| **问题** | 客户端按显示名发请求时记账键为 `OC · 名称`，探测用全限定 id，两键并存且互斥，导致失败模型的 `validated.remove` 落空，坏模型永久留在可用池并被反复选中 |
| **证据** | `space-bunny-free`：全限定键 ok(probe) + 显示名键 502(request,2次) 并存，`availableModels` 仍含它；同类污染 3 个键 |
| **目标** | 同一模型的成功/失败判决必须命中同一个记账键 |
| **范围** | `protocol.rs`（或 `server.rs`）的记账键归一化 + `orchestration.rs::record` 兜底；**不改** `prepare` 的匹配放宽语义（那是存量兼容面） |
| **方案** | 在取记账键处把显示名**反向归一**为全限定 id（建 `client_id → id` 映射，映射不命中则保留原值），使 `validated` / `modelResults` / `usage.models` 三处键语义统一到全限定 id；同时清理历史双键（`modelResults` 里同一模型的显示名键合并进全限定键） |
| **依赖** | 无外部依赖；需注意 `js_parity` 夹具是否含显示名入参（须复查，避免对拍分叉） |
| **风险** | 中。改记账键会改变 `status.json` 的键形态，面板若按显示名读 `modelResults` 需同步；`usage` 历史键断裂（可接受，或用保留期内双读过渡） |
| **验收信号** | ①新增单测：客户端以显示名发请求失败后，全限定键即刻从 `availableModels` 消失；②实机复现：让一个模型连续失败，面板与 `/v1/models` 当次即收缩；③`git diff --stat tests/fixtures` 为空 |

### 3.2 【R-02】WB · auto 的 `maxInputTokens` 取池内最小值 → 容量浪费 122 倍 🔴 P1

| 要素 | 内容 |
|---|---|
| **问题** | `sync.rs::smallest_input` 取池内最小 `input`（v1.1.15 由用户选定的保守口径），混搭池下把长上下文模型砍到最小桶 |
| **证据** | 真实池最小 `8192`（`siliconflow-cn/deepseek-ai/DeepSeek-OCR`），最大 `1000000`（`opencode/step-5-preview-free`）；插件侧写入的 `WB · auto` 实测 `maxInputTokens = 8192` ⇒ **122.1×** 浪费 |
| **目标** | 既保守（不承诺可能撑不住的上下文）又不显著浪费容量 |
| **范围** | `sync.rs::smallest_input` / `auto_entry` |
| **方案** | 三选一待裁：**(A)** 取池内**中位数**或**保守分位（如 P25）**；**(B)** 取「工具/文本主档（非 OCR 等专用模型）」子集的最小值，把专用小模型排除出统计域；**(C)** 不写该键（由插件自行决定，但可能失去截断保护）。推荐 **B**：语义最正——把 OCR 这类专用模型排除后，最小值回到 32768（4× 改善），且守住真实性 |
| **依赖** | 需先确认插件在无 `maxInputTokens` 时的行为（B 方案不写键则退化为 C） |
| **风险** | 低（只影响写入插件配置的一个字段）；但选 A/B 需要一次插件侧实机验证确认不再提前截断 |
| **验收信号** | 实机：写入的 `maxInputTokens` ≥ 32768；/ 或该键不写且插件发长上下文请求不截断 |

## 四、优先级评估机制（Phase 4）

### 4.1 评分模型：加权 RICE+（针对本项目裁剪）

本项目是**单人/小团队维护的工具型产品**，用户价值高度集中在「让模型持续可用」这一件事上。因此引入 **Blocks-Core（是否阻断核心承诺）** 作为一票上抬因子。

```
Score = (Reach × Impact × Confidence) / Effort  × BlocksCore_Multiplier
```

- **Reach**（1-5）：受影响用户比例。本项目用户面集中，故取 1-3 为主。
- **Impact**（1-5）：对用户核心诉求的改善强度。
- **Confidence**（0.5-1.0）：证据强度。实机取证=1.0；逻辑推演=0.7；推测=0.5。
- **Effort**（人日，0.5 起）：含修复 + 验证 + 文档。
- **BlocksCore**：是否阻断「失败自动摘除 / 模型持续可用」这一产品核心承诺。是 = ×2.0，否 = ×1.0。

## 八、结论摘要

1. **最大发现不是缺陷，而是台账失真**：项目实际状态远好于文档自述——GUI 已在跑、1.1.15 已发布、WB · auto 已端到端、4 个平台 Key 已生效、37 次真实请求。先把台账校准，否则所有决策都建在错误信息上。
2. **唯一 P0 已抓到且证据确凿**：记账键双形态并存让「失败即摘除」完全落空（`space-bunny-free` 失败 2 次仍在发布）。Effort 仅 1 人日，BlocksCore 让它必须排第一。根因是 v1.1.14 的 D2 只归一化了 `WB · auto` 这条路，手动选模型的路径被漏掉。
3. **一个被文档预判、被实机证实的缺陷**：`maxInputTokens` 取最小值导致 **122× 容量浪费**（8192 vs 1000000）。这是「 conservative 默认值选错粒度」的典型案例，改起来半天。
4. **发布了三轮、装了三轮，但从没人走完一次应用内升级**：这是当下最大的价值洼地——R-03 只需一次验证操作，就能解锁「用户不必手动下载」这一核心体验。
5. **工程纪律是本项目最大的资产**：316 项测试、JS↔Rust 对拍、红线测试、7 处版本闸门、发布前资产对账——这些都已跑通且可靠。下一阶段应该**依赖它、补全它**（R-09），而不是绕开它。
