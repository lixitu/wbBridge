## 校验与推进

```bash
npm run version:check                 # 校验 5 处落点一致，否则退出码 1
npm run version:set -- <x.y.z>        # 同步改写各落点
```

`version:check`（`scripts/check-version.mjs`）校验 **5 处**：`package.json`、`src-tauri/tauri.conf.json`、`src-tauri/Cargo.toml`，以及 `AGENTS.md` 的两行基准表。`release.yml` 的测试 job 也声明了同一脚本，并加了一道**标签↔版本闸门**；该工作流**已于 2026-10-03 跑通完整一轮**（tag `v1.0.2`、run `37092915120`、8/8 作业全绿），闸门与脚本在 CI 上确实执行过，但**同轮 `latest.json` 的 url 缺陷说明「CI 全绿」不等于发布物可用**（见「签名与自动更新」）；改动版本号后仍建议再 `grep -rn "1\.0\.1"` 人工扫一遍文档。

## 版本号规则（写死）

- 版本号以**根 `package.json`** 为唯一来源；`src-tauri/core/Cargo.toml` 的 `0.1.0` 是 crate 内部版本，`status.json` 的 `0.2.0` 是历史沿革值，**两者都不得在无用户指令的情况下静默改动**。
- **仅当**新增了与现有问题**不同类、不同根因**的功能 / 修复，且**用户明确允许**推进版本号时，才可末位 +1。
- **以下情形绝对禁止推进版本号**：
  1. 同一问题的多轮往返排查与再次修复；
  2. 用户明确要求"不修改版本号 / 回退到 X.Y.Z"；
  3. 同一自然日对同一模块 / 同一类 bug 的追加修复；
  4. 纯 `docs/`、`README.md`、`AGENTS.md` 等文档类改动；
  5. 纯文案、注释、日志措辞、去抖等不引入新逻辑分支的打磨；
  6. 移植 / 迁移过程中的等价实现（行为未变即版本未变）。
- 用户要求"回退到 X.Y.Z"时，所有落点必须一致改写为用户指定值，本回合内不得再以"我刚改了代码所以 +1"为由推进。

> 界面调整同样不推进版本号：2026-10-01 的面板布局改造（侧栏分组导航、详情改为右侧常驻分栏、默认窗口 980×680 → 1120×720、侧栏 `--sidebar-w` 224 → 208px、新增 `--muted-strong`）属同一未发布版本内的界面调整，已在 `docs/version/RELEASE-v1.0.md` 的 v1.0.0 分节留痕。
> 后续说明（2026-10-01 同日）：该轮留下的 4 个「规划中」入口已在同日后续轮次实现（侧栏 5 入口全部可点，新增壳命令 `read_log` 与 `status.json` 顶层 `usage`），本版本内同样不推进版本号；证据见 `docs/validation.md`。
> 版本推进（2026-10-01 同日第八轮）：用户在本次**明确要求推进版本号**后，产品版本 `1.0.0 → 1.0.1`（5 处落点一致，`npm run version:check` 通过）；v1.0.0 分节从未发布，内容并入本次。依据见 `docs/version/RELEASE-v1.0.md` 顶部 v1.0.1 分节与 `docs/validation.md` 同轮条目。

### CI 工作流

`.github/workflows/release.yml`：推送 `v*` tag 或手动 `dispatch` 触发。

1. **test 作业**：跑 `cargo test`（核心）+ `check-version.mjs` + 三组 `node --test`（步骤名「运行面板偏好、更新清单与签名注入单测」：prefs 8 / manifest 9 / updater-key 13），外加一道**「触发标签 ↔ `src-tauri/tauri.conf.json` 版本」闸门**（标签指向未推进版本的提交时直接失败）。
2. **平台构建作业**（macOS / Windows / Linux 各 2 架构）：`npm ci` + `npm run tauri:build -- --target <triple>`（= 经签名注入包装器跑 `tauri build`；macOS 那步另带 `--bundles app`），签名变量取自 `vars.TAURI_SIGNING_PRIVATE_KEY{,_PASSWORD}`。**2026-10-03 起不再使用 `tauri-apps/tauri-action`**，Release 由 `softprops/action-gh-release` 创建，`tag_name: v<version>` 由「读取版本号」步骤现读 `tauri.conf.json` 拼成（否则 `workflow_dispatch` 触发时会把分支名当标签、另开一个 Release）。
   - macOS 作业在构建后多两步：`npm run make:dmg`（**必须带 `TARGET_TRIPLE`**，否则 `uname -m` 反映的是 runner 架构）与**「给 macOS 更新包补架构后缀」**——tauri 实测产出的更新包叫 `WB Bridge.app.tar.gz`（无版本、无架构），两个 mac runner 会往同一 Release 传**同名**资产、后者静默覆盖前者，因此统一改名为 `WB Bridge_<arch>.app.tar.gz`（`.sig` 同步改名——minisign 签的是内容不是文件名）。✅ 该步在 `v1.0.2` 那轮已实测生效：Release 上是 `WB Bridge_aarch64.app.tar.gz(.sig)` 与 `WB Bridge_x86_64.app.tar.gz(.sig)`，没有互相覆盖。
3. **update-manifest 作业**（末位、`latest.json` 的唯一写者）：下载六平台产物 → `node scripts/gen-latest-json.mjs --dir artifacts --out latest.json` → **「校验清单 url 指向的资产在 Release 上真的存在」**（2026-10-03 新增：带 `GITHUB_TOKEN` 列 Release 资产，把六条 url 末段与实际资产名逐条对账，任一不符 `exit 1`）→ 产物版本自检 → 上传清单到 Release。三个 build 作业**谁都不写清单**（`tauri-action` 自带的清单生成当初已用 `includeUpdaterJson: false` 关闭——6 个并发作业各写一次会互相覆盖、静默漏平台；2026-10-03 起连 `tauri-action` 本身都已撤掉）。⚠ 新增的对账步骤本身**尚未在 CI 上实跑过**。
4. 产物：六平台（macOS ARM/Intel、Windows x64/ARM、Linux x64/ARM）安装包 + 各自 `.sig` + `latest.json`，发布为 **Draft Release**；人工确认后再点 Publish。

> ⚠ 如实说明：核心 Rust 化后重写的 `release.yml` **已于 2026-10-03 跑通完整一轮**（tag `v1.0.2`、head `0e4a535`、run `37092915120`、**8/8 作业全绿**，Release 已 Publish、**23 个资产**）；同日更早的首次实跑曾止步于 updater 签名步骤（私钥变量取到空值，见下「签名与自动更新」）。**但那一轮的 `latest.json` 六条 `url` 全部 404**（GitHub 把资产名里的空格规范化成 `.`），脚本与 CI 闸门已修、线上清单待重传，一次真实升级闭环仍未走过。README 中关于「CI 构建」的更早历史构建结论仍属迁移前记录。

### 签名与自动更新

- **自动更新已接线**：`src-tauri/Cargo.toml` 有 `tauri-plugin-updater` + `tauri-plugin-process`，`lib.rs` 的 builder 链注册两者，`tauri.conf.json` 有 `bundle.createUpdaterArtifacts: true`、`bundle.targets` 为显式列表 `["app", "nsis", "msi", "appimage", "deb"]`（本平台不适用的目标由打包器跳过；**不含 `dmg`**）与 `plugins.updater`（内联 `pubkey`，当前**恰好一条**公钥 `2B11F78BEA8A43F` + `endpoints` 指向 `https://github.com/trexwb/wbBridge/releases/latest/download/latest.json`）；capabilities 声明 `updater:default` + `process:allow-restart`（刻意不用 `process:default`，它含 `allow-exit`，会让 WebView 绕过 `quit_app` 的优雅关停链）。
  - **签名变量分工（实测）**：`tauri build|bundle` **只读 `TAURI_SIGNING_PRIVATE_KEY`**，值可以是私钥全文**或私钥文件路径**（`~` 由本仓包装脚本展开，Node 与 `tauri build` 自己都不展开 `~`）；`TAURI_SIGNING_PRIVATE_KEY_PATH` 只对 `tauri signer sign` 生效（等价于 `-f`），包装脚本把它读成内联全文后**删掉**——CLI 的内联值与 `--private-key-path` 互斥，同时给会被拒。`signer sign -k` 要的是**私钥字符串**，误传路径会报 `failed to decode base64 secret key: Invalid symbol 46`。
  - **CI 变量位置（2026-10-03 按用户决定）**：`.github/workflows/release.yml` 读仓库级 **Variables**（`vars.TAURI_SIGNING_PRIVATE_KEY` = 私钥**内联全文** + `vars.TAURI_SIGNING_PRIVATE_KEY_PASSWORD`），对齐参考项目 fastenerTradeWorkbench / lockPass。⚠ 代价如实记录：**Variables 是明文值**（设置页直接可见、日志里**不像 Secrets 那样打码**），因此工作流绝不 echo 这两项，包装脚本也只打印**来源文件名与公开的 key ID**；想换回 Secrets 只需把 `vars.` 改回 `secrets.`，脚本与命令都不用动。CI **刻意没有**私钥前置校验步骤。
  - **签名注入包装器 `scripts/with-updater-key.mjs`（已接入构建链，不是可选自检）**：`npm run tauri:build` = `node scripts/with-updater-key.mjs tauri build`，`npm run build` = `vite:build && tauri:build && make:dmg`，CI 三个平台作业也走同一条。它**只做注入、不做前置校验**——**不判私钥形态、不试签、公私钥配对不符也只告警不阻断**，最后 exec 目标命令。取值顺序（前者命中即止）：**进程环境 > 仓库 `.env.local` > 仓库 `.env` > `~/.tauri/wbBridge.env` > `~/.tauri/wbBridge-updater.env` > 兜底 `~/.tauri/wbBridge-updater.key`**，逐项独立取值并打印**来源文件名**（钥来自环境、口令来自 `.env.local` 的混搭曾让报错只剩「口令不对」）；环境变量里只要**存在** `..._PASSWORD` 就按显式处理，显式空串＝「这把钥无口令」，不再回落文件。`.key` 路径会被读成内联全文并 **trim**（尾部换行会让 tauri 报 `Invalid symbol 10`）；明文（未加密）钥会被**显式**置空口令，否则无 TTY 的运行会以 `Device not configured (os error 6)` 死掉。私钥与口令**全程不打印**。早前导出的 `resolveKey` / `checkKeyShape` / `configuredKeyIds` / `checkPairing` / `classifySignerError` / `dryRunSign` 与 `--check-only` 入口已随 2026-10-03 的注入器重写**移除，不要再按旧名调用**；要构建就走 `npm run tauri:build` / `npm run build`。逻辑由 `npm run test:updater-key`（`node --test`，**13 通过 / 0 失败**）钉死，不联网、不调 tauri CLI、不碰真实私钥。

### 失败路径与回滚

| 失败点 | 面板行为 | 服务影响 |
|---|---|---|
| 检查更新失败（endpoint 404 / 网络不可达 / 清单签名不符） | 「关于与更新」的更新区显示具体原因（`FeedbackBar` 错误态，可关闭）；**冷启动的静默检查失败完全不提示** | 无。探测与请求链路不经更新器 |
| 下载或安装失败（含**清单 url 指向的资产名在 GitHub 上取不到**——2026-10-03 实测：GitHub 把资产名空格规范化成 `.`，空格/`%20` 形式的 url 一律 404，此时**手动到 Release 页下载安装包**即可绕过） | 更新条保留、按钮回到「下载并安装」，错误可见并可原地重试（`bridge.js` 只在成功时清空 Update 句柄） | 无。**不存在"半更新"**：安装失败即视为未安装，当前版本继续运行 |
| 装完点「重启应用」 | `process.relaunch` → `ExitRequested` → 壳的**有界**停止（`stop_core_bounded`）→ 重启 | 重启路径与关窗退出共用同一条优雅关停链，不为更新另开退出通道 |
| 更新后首启失败 | 面板收到 `core-failed`，`phase: error` + 原因（该事件在故障期每 ~4s 重播，晚挂载的监听也能收到） | 核心不重试拉起；用户可按下表回滚 |

**回滚兜底（手动装回上一版）**：每个已发布版本的安装包必须保留在 Release 页（Draft→Publish 后不删除资产）。步骤：

1. 「关于与更新」记下当前面板版本；
2. 托盘或关窗彻底退出应用（关窗即退出，无需二次操作）；
3. 到 Release 页下载上一版安装包（macOS `.dmg` / Windows `-setup.exe`）；
4. 覆盖安装后启动。**数据目录不用动**：`api-key`、`settings.json`、`status.json` 与托管的 OpenCode 运行时都在应用数据目录，跨版本复用；
5. 若该版本的模型发布结果与新壳不一致，回到「模型与服务」点一次「读取免费模型」→「检测全部」→「导入 WorkBuddy」即可（核心只增删自己名下的条目）。

> ⚠ 以上四条失败路径的**代码行为已实现**，但「点重启 → 新版本起来 → 首启失败 → 手动回滚」这条**完整链路仍未实机走过**（需要一次真实的 v1.0.3 → v1.0.4 发布才能验证）。

1. **顺序铁律**：先 `npm run version:set -- <x.y.z>` 改写 5 处落点并**提交**，再**在那一个提交上**打 `v<x.y.z>` 标签。标签永远不允许指向"不含本次版本推进"的提交。
   - 反面教材：`v1.0.1` 第一次打在 `f046208`（仍写 1.0.0、落后 4 个提交），产物因此叫成 `WB Bridge_1.0.0_aarch64.dmg`。
   - 2026-10-02 实读的标签现状（`git show-ref` + `git ls-remote --tags` + `git show <tag>:<文件>`）：**远端** `v1.0.1` 已被维护者改指 `679a2cb`（Merge PR #2；该提交的 `package.json`、`tauri.conf.json`、`src-tauri/Cargo.toml`、`src-tauri/Cargo.lock`、`AGENTS.md` 全部为 `1.0.1`，且历史里含版本推进提交 `46c7c56`，顺序铁律已满足）；**本地** `v1.0.1` 仍指 `f046208`，`v1.0.0` 两侧都指 `f046208` 未动。本地标签落后属**共享状态同步**，需维护者自行 `git fetch --tags --force`（或按需重打），Agent 不得代劳。
   - 远端 `v1.0.1` 那次推送**是否真的触发过 CI、Release 页有无资产，本机无法核验**（无 `gh`、不联网查证），所以「CI 已跑通 / 有已发布安装包」仍按未验证处理。
   - 删除 / 移动**已推送**的标签属共享状态变更，只能由维护者本人执行。
2. **CI 闸门**（`release.yml` 的 test 作业，`check-version.mjs` 之后一步）：`GITHUB_REF_NAME` 去掉前导 `v` 后必须等于 `src-tauri/tauri.conf.json` 的 `version`，不一致 **exit 1**；`workflow_dispatch` 触发时 `GITHUB_REF_NAME` 是分支名，该步骤整体跳过。
   - 为什么单加一道：`check-version.mjs` 只校验**同一提交内**各处落点互相一致，标签指向"全体都是旧版本"的提交时它照样绿。
   - 版本还决定 Release 的标签名：2026-10-03 起由「读取版本号」步骤现读 `tauri.conf.json` 拼成 `tag_name: v<version>` 交给 `softprops/action-gh-release`（不再经 `tauri-action` 的 `tagName: v__VERSION__`），不一致会同时开出两个 Release。
3. **产物名自检**：三个 build 作业在上传前各自 `find` 打印 bundle 文件名与源码版本；末尾 `update-manifest` 作业汇总六平台实际收到的安装包，统计「文件名含本次版本 / 按设计不含版本（macOS 更新包）/ 待人工核对」三类，并把结论写进 run summary（可直接引进 Release 正文）。**待核对项不为 0 时不要点 Publish**。
   - ✅ 该自检已在 2026-10-03 的 `v1.0.2` 完整一轮里真实跑过（8/8 作业全绿），六平台安装包的最终命名也已由那一轮的资产清单确认（见「安装包命名」）。⚠ 但**同轮的 `latest.json` 六条 url 全部 404**——产物名自检与「清单 url ↔ 实际资产名」是两回事，后者靠新增的那道对账步骤，而它本身还没在 CI 实跑过。
