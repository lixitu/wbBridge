# 常见问题与故障排查

本页按症状组织。所有阈值、错误码与文件路径均来自仓库真实实现（`src-tauri/core/src/*`、`src-tauri/src/lib.rs`、`docs/contract.md`、`AGENTS.md`）。

## 排查先决条件：确认运行形态与数据目录

两种运行形态**共用同一份编排代码，但数据目录互不相通**，排查前先确认用的是哪一个：

| 形态 | 数据目录 | 端口 |
|---|---|---|
| 桌面壳（正式形态） | Tauri `app_data_dir`（macOS `~/Library/Application Support/app.wbbridge.desktop`） | `pick_port()`：默认 41980，被占用时回退到系统空闲端口，**以 `status.json` 的 `endpoint` 为准** |
| 独立核心二进制 | `BUDDY_DATA_DIR`，否则平台默认（macOS `~/Library/Application Support/Buddy Bridge`、Windows `%APPDATA%\Buddy Bridge`、Linux `${XDG_CONFIG_HOME:-~/.config}/Buddy Bridge`） | `BUDDY_PORT`，默认 41980 |

数据目录内可查文件：`api-key`（Bearer 令牌）、`service.pid`、`settings.json`、`status.json`（状态唯一来源）、`opencode.log`（子进程日志，超 5MB 轮转）、`runtime/<version>/opencode`、`opencode/{config,data,cache,state,project}`。

## 启动类问题

### 启动即退出，提示已在运行

- **原因**：数据目录下 `service.pid` 指向的进程仍存活，触发单实例锁（`ALREADY_RUNNING`）。
- **处理**：确认该进程是否为本应用；独立运行核心二进制时重复启动会以**退出码 2** 结束。不要删除 `service.pid` 绕过锁——单实例锁是数据红线之一。

### 启动失败：端口不合法

- **原因**：`BUDDY_PORT` 不是 **1024–65535** 范围内的整数时，核心直接失败退出（独立进程按退出码 1）。
- **处理**：改用合法端口，或不设置该变量让它取默认 `41980`。

### 服务起来了但 `phase` 一直不进入 `ready`

- **原因**：启动时序第 8 步的 `/agent` 校验未通过——隔离配置中的 `buddy-bridge`、`buddy-chat` 两个自定义 agent 必须存在。
- **排查**：查看 `status.json` 的 `phase` 与 `opencode.log`。

### 运行时（OpenCode）准备失败

- **可能原因**：
  - 下载失败：registry 顺序为 `registry.npmjs.org` → `registry.npmmirror.com`，两者都不可达。
  - 校验失败：元数据 `dist.integrity` 必须以 `sha512-` 开头，且 tarball 必须来自白名单 registry；**校验失败不得跳过重试**（这是供应链红线，测试已固化该行为）。
  - 版本回读不一致：安装后回读 `--version` 必须与元数据版本一致。
  - 本地候选被拒：`.cmd` / `.bat` / `.ps1` 启动器脚本不作运行时；版本必须形如 `x.y.z`。
- **处理**：优先用 `BUDDY_OPENCODE_PATH` 指定本机可信的 `opencode` 可执行文件；或检查网络与代理设置。
- **注意**：本地已有可用版本时会被复用，不会重复下载。

### 卡在"正在读取免费模型"

- **原因**：启动导入会**逐模型真实探测**，每个模型有 `PROBE_TIMEOUT_MS = 60000` 的预算，模型多时整体耗时较长。
- **说明**：这一步会消耗少量免费额度（发送简短真实请求），属预期行为，不是卡死。

## 网络与鉴权类问题

### `curl` 返回 401

- **原因**：`/health` 与所有 `/admin/*`、`/v1/*` 路由**都要求** `Authorization: Bearer <api-key>`；裸 key 或非 Bearer 方案一律 401。
- **处理**：用**当前运行形态**对应的数据目录里的 `api-key`：
  ```sh
  # 独立核心二进制
  curl -H "Authorization: Bearer $(cat "$HOME/Library/Application Support/Buddy Bridge/api-key")" \
       http://127.0.0.1:41980/health
  # 桌面壳形态（端口见同目录 status.json 的 endpoint）
  curl -H "Authorization: Bearer $(cat "$HOME/Library/Application Support/app.wbbridge.desktop/api-key")" \
       http://127.0.0.1:41980/health
  ```
- **常见误区**：两套目录混用。壳形态的 key 与端口都取自 `app_data_dir`。

### 返回 403

- **原因**：请求带了任意**非空** `Origin` 头。设计上 WorkBuddy 只经其原生运行时访问本服务，浏览器来源一律拒绝。
- **处理**：用命令行工具（不带 Origin）访问，勿从浏览器页面发起。

### 返回 429 busy

- **原因**：并发上限为 **4**，超出返回 429。
- **处理**：降低并发；这是限流红线，不可放宽。

### 返回 413

- **原因**：请求体超过 `MAX_BODY_BYTES = 8MB`。
- **处理**：缩小请求体（如减小图片体积 / 数量）。

### 请求体读取超时（20s）

- **原因**：`REQUEST_BODY_TIMEOUT = 20s`。客户端在慢网络下上传大体积请求体可能触发。

### 流式响应中途长时间无数据

- **说明**：SSE 有 `DEFAULT_HEARTBEAT = 10s` 的注释行心跳。若超过心跳间隔仍无任何字节，说明连接可能已断，应检查客户端与网络。

### 所有模型探测报 `self signed certificate`

- **症状**：面板上所有模型显示「不可用」，`status.json` 的 `modelResults` 中每条 `error` 均为 `"self signed certificate"`，`nativeAttempts: 0`。
- **原因**：OpenCode (Bun 运行时) 向上游模型 API 及 `https://models.opencode.ai/api.json` 发 HTTPS 请求时遇到 TLS 拦截（公司代理 / VPN / ZScaler / Charles Proxy 等）。Bun 不读取 macOS 系统钥匙串，即使拦截证书已安装到系统钥匙串也不信任它。
- **排查**：查看数据目录下 `opencode/data/opencode/log/opencode.log`，搜索 `self signed certificate` 或 `Failed to fetch models.dev`。
- **处理**：v1.0.5 起在 `isolated_environment` 中设置了 `NODE_TLS_REJECT_UNAUTHORIZED=0`，让 Bun 跳过 TLS 证书验证。升级到 v1.0.5+ 即可解决。

## 模型与配置类问题

### 面板顶部「导入 WorkBuddy」提示找不到配置

- **原因**：models 文件路径解析遵循 `BUDDY_MODELS_FILE` → `settings.json` 已保存值 → WorkBuddy 配置目录发现；全部失败时返回 null，**绝不静默回退**到猜测路径。
- **处理**：
  1. 先在 WorkBuddy 中保存一个自定义模型（生成 `models.json`）；
  2. 点面板「导入 WorkBuddy」手动选择 `models.json`；
  3. 之后若位置变化，可用托盘菜单「选择 WorkBuddy 配置…」重新指定。

### 面板显示 0 个模型

- **可能原因**：
  - 免费模型发现为空：免费判定要求输入 / 输出 / 缓存价格全为 0、输出支持文本、且**非 deprecated**；
  - 探测全部未通过：只有 `ok` 的模型会进入发布集；
  - 上游确实暂无可用免费模型（名单与额度由上游决定，本应用不控制也不缓存额度）。

### 某个模型探测失败后"重试一次"仍失败

- **说明**：每个模型有 60s 预算，重试**共用同一 deadline**；预算耗尽即判定失败。仅 `ok` 模型会被发布。

### 已发布模型在请求时报 `invalid_model_output` / `invalid_tool_call` / `native_tool_activity` / `output_truncated`

- **说明**：这些属于**格式类上游失败**（`REQUEST_SHAPED_FAILURES`）。
- **行为约定**：
  - 这类失败**不会撤销**已发布模型；
  - 非探测路径会先做一次格式修正（`resend_prompt`，只纠正格式），仍失败则由辅助模型转写一次（候选来自 `TRANSLATOR_ORDER`，且**排除刚失败的模型**）；
  - **探测路径禁止转写**；
  - 纯文本模型（`buddy-chat`，chatOnly）遇到原生工具活动会报 `native_tool_activity`，不会降级为静默执行。

### 模型想执行本地操作却没有执行

- **说明**：这是**设计行为**。原生工具权限为 `'*': 'ask'`，`question` / `websearch` / `codesearch` / `webfetch` / `task` / `plan_enter` / `plan_exit` / `todowrite` 为 `deny`；原生动作只能以 handoff 交回客户端，模型不得自行执行本地动作。

### WorkBuddy 里的手动模型被改动了吗？

- **不会**。写入 `models.json` 时只清理 / 更新 `OWNER = 'buddy-bridge-v1'` 名下的条目，其他条目与对象元数据原样保留；写入走原子写 + 5 分钟锁过期 + 写前二次读取，**不再产生 `.bak` 备份文件**（旧版本攒下的同族备份会在下一次同步时自动清掉，你自己命名的 `*.bak` 不碰）；手动条目 ID 冲突时不擅自覆盖。退出时清理**只涉及自己名下**的条目。

## 代理类问题

### 打开了「使用系统代理」但似乎没生效

- **说明**：系统代理解析仅支持 macOS（`scutil --proxy`）与 Windows（注册表）；解析结果注入 OpenCode 子进程环境。**解析失败会回退为关闭且不阻断启动**。
- **限制**：**PAC / SOCKS 代理暂不支持**（与原版一致）。
- **处理**：确认系统为手动 HTTP/HTTPS 代理模式，而非 PAC 自动配置或 SOCKS。

## 界面与托盘类问题

### 点右上角关闭按钮后会发生什么

- **说明**：关闭窗口**就是退出应用**（macOS / Windows / Linux 一致）。壳先隐藏窗口，再走与托盘「退出」相同的优雅关停：停止核心、清理 WorkBuddy 配置、结束进程；不再有「窗口关了但服务仍在后台跑」的驻留状态。
- **耗时**：关停预算 `STOP_BUDGET = 8s`。超时则记录日志并交由核心的父进程看门狗（`BUDDY_PARENT_PID`）自行收尾，不留占端口的孤儿进程。
- ⚠ 该行为**尚未在真实 GUI 中实测**（本仓库 GUI 验证边界未解除），证据只有编译与单元测试。

### 怎么彻底退出

- **方式**：直接关闭窗口，或从托盘菜单「退出 WB Bridge」——两者走同一条链路，优雅停止服务（预算 `STOP_BUDGET = 8s`）并完成 WorkBuddy 配置清理。

### 侧栏那几个入口分别是什么

- **说明**：侧栏 5 个入口都已实现，点击即切换主区——**模型与服务**（默认视图，模型列表 + 详情）、**运行日志**（只读展示核心日志尾部，可点「刷新」重新拉取）、**用量与额度**（累计真实请求计数，只统计客户端请求）、**WorkBuddy 集成**（只读展示配置定位与发布结果，可在这里复用「导入 WorkBuddy」）、**关于与更新**（版本与数据目录 + 自动更新区：启动后静默检查，发现新版本才出现「下载并安装」）。

### 点了「检查更新」什么都没发生 / 报网络错误

- **先确认版本**：**v1.0.1 及更早的安装包没有接入更新器**（产物里没有 `.sig`、面板也没有更新区），那一版的用户只能重新下载安装包升级一次；从 v1.0.2 起才有应用内更新。
- **静默检查失败不打扰**：启动后的自动检查是静默的，失败只留在状态里、不弹提示；手动点「检查更新」才会把原因显示出来。
- **拿到 404 通常是正常的**：更新清单地址是 `.../releases/latest/download/latest.json`，而 GitHub 的 `releases/latest` **不包含 Draft 与 Pre-release**。新版本发出来要先人工点「Publish release」，在那之前老客户端必然查不到更新——这是灰度闸门，不是故障。
- **清单查得到、下载那步却 404**（2026-10-03 在 `v1.0.2` 首跑实测到的缺陷）：GitHub 上传时会把 Release **资产名里的空格规范化成 `.`**（磁盘上 `WB Bridge_1.0.2_x64-setup.exe` → GitHub 侧 `WB.Bridge_1.0.2_x64-setup.exe`），而 `/releases/download/<tag>/<空格名>`（含 `%20`）**一律 404**。清单的 url 因此必须先把空格换成点再编码（`scripts/gen-latest-json.mjs` 已改，`npm run test:manifest` 的成功路径断言已钉住，`update-manifest` 作业另加了一步「校验清单 url 指向的资产在 Release 上真的存在」逐条对账）。**线上那份 v1.0.2 的 `latest.json` 仍是旧的坏清单**（重传属共享状态、由维护者操作），在它被覆盖之前老客户端能查到更新但拉不到包——此时手动到 Release 页下载安装包即可。
- **下载完成后不会自动替换**：装完停在「待重启」，由用户点「重启应用」，重启走壳的优雅停止链路（先停核心、清理 WorkBuddy 配置，再 relaunch），中途关闭窗口同样会走这条链路。

### 「启动后自动检查更新」开关（在「关于与更新」里）

- **口径**：关掉后冷启动不再自动请求更新清单，「检查更新」按钮仍随时可用；打开时按 **12 小时**节流（距上次**成功**查到清单/确认已是最新不足 12 小时就不再重复打端点）。
- **持久化**：该开关与当前视图都存面板 `localStorage`（键前缀 `wb.`，只允许白名单字段）；换视图、重启应用后仍回到上次的视图。
- **拿不到存储就静默降级**：`localStorage` 不可用或被禁用时用默认值（自动检查=开、视图=模型与服务），不报错、不阻断启动。
- ⚠ 上述持久化只有 `npm run test:prefs` 的 8 项单测与构建证据，**未在 Tauri GUI 里实测**。

### 更新装完重启后启动失败（`phase: error` / 面板报 `core-failed`）

- **先分清是哪一层失败**：更新器负责替换应用镜像，核心负责启动。若面板能打开且显示「核心启动失败：<原因>」，说明壳已装好、是核心侧的启动问题（运行时、端口、models 文件路径等），按上面「启动类问题」逐条排查即可，不必回滚。
- **确认应用版本**：看「关于与更新」的「面板版本」，与更新条上的版本号对得上，说明镜像替换成功。
- **回滚兜底（手动装回上一版）**：每个版本的安装包都保留在 Release 页不删资产。步骤是「彻底退出 → 下载上一版安装包 → 覆盖安装 → 启动」；**数据目录不用动**（`api-key`、`settings.json`、`status.json`、托管的 OpenCode 运行时都在应用数据目录，跨版本复用）。完整口径见[版本与发布](版本与发布)的「失败路径与回滚」。
- ⚠ **不存在"半更新"状态**：下载或安装失败即视为未安装，当前版本继续运行、可原地重试；因此回滚只需要重装上一版安装包，不需要清理数据目录。
- ⚠ 「点重启 → 新版本起来 → 首启失败 → 手动回滚」这条**完整链路仍未实机走过**（需要一次真实的 v1.0.3 → v1.0.4 才能验证）。

### macOS 更新后仍被 Gatekeeper 拦下

- **原因**：macOS 只有 ad-hoc 签名、**未做 Apple 公证**；经更新器替换镜像后，Gatekeeper 有可能重新判定为「已损坏」（商用签名/公证属 A7 预留位，尚未接入，见[版本与发布](版本与发布)）。
- **处理**：按下面「macOS 提示"无法打开"或"已损坏"」的 `xattr` 步骤放行；若反复出现，直接重新下载 `.dmg` 覆盖安装。

### 打开「运行日志」是空的

- **说明**：日志页只读核心数据目录下 `opencode.log` 的尾部。若核心尚未拉起运行时、还没产生日志，页面就是空的（不是故障）；截断发生时页面上会有提示，点「刷新」可重取尾部。

### 详情栏怎么收起

- **三种等价路径**：按 `Esc`、点详情头部「收起详情」按钮、或窗口失焦。收起即清空选中，列表占满主区宽度。

### 深色/浅色主题下有些小字偏淡

- **已知问题**：浅色主题下仍有 3 处次要文字（副标题、页脚说明、耗时行）沿用 `--muted`，对比度低于 WCAG AA 的 4.5:1，属既有问题尚未处理。详见[已知限制与未验证项](已知限制与未验证项)。

## 安装类问题（macOS / Windows）

### macOS 提示"无法打开"或"已损坏"

- **说明**：应用使用 ad-hoc 签名（**未做 Apple 公证**）。
- **处理**：先尝试打开 →「系统设置 → 隐私与安全性」→「仍要打开」；若提示「已损坏」，确认来源可信后执行：
  ```sh
  xattr -dr com.apple.quarantine "/Applications/WB Bridge.app"
  ```

### Windows 提示"未知发布者"

- **说明**：未做商用代码签名，属已知限制。

### 找不到安装包

- **说明（重要）**：**六个平台的安装包都已由 CI 产出并发布在 Release `v1.0.2` 上**（2026-10-03，tag `v1.0.2`、run `37092915120`、8/8 作业全绿、23 个资产）；本机则只构建过 **macOS Apple Silicon**——2026-10-03 按 `npm run build` 的三个环节逐段跑通（`vite:build` → `npm run tauri:build -- --bundles app` → `npm run make:dmg`，退出码均 0），产出 `src-tauri/target/release/bundle/dmg/WB Bridge_1.0.2_aarch64.dmg`（4,077,548 B，约 3.9 MB，由 `scripts/make-dmg.sh` 用 hdiutil 生成，**不再由 Tauri 产出 dmg**）与 updater 包 `bundle/macos/WB Bridge.app.tar.gz`（3,596,811 B）+ 配对 `.sig`（428 B）；该 `.app` **未实际运行过**，其余五平台的包**只在 CI 上构建过、没有实机跑过**。
- **处理**：到 Release 页取对应平台的资产即可（注意 GitHub 把资产名里的空格规范化成 `.`，页面上看到的是 `WB.Bridge_1.0.2_x64-setup.exe` 这种名字）。自行触发构建时，仓库级 **Variables** 里要有 `TAURI_SIGNING_PRIVATE_KEY` 私钥全文**与非空口令** `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`，缺任一项则三个 build 作业会跑完整套 Rust 编译、在生成 updater 产物那一步失败；CI 走 `npm run tauri:build -- --target <triple>`，macOS 另跑 `npm run make:dmg` 并**必须传 `TARGET_TRIPLE`**。实测到的产物名（含架构与版本）见[版本与发布](版本与发布)「安装包命名」。

### CI 构建在签名那步报 `Missing comment in secret key`

- **症状**：`Error failed to decode secret key: incorrect updater private key password: Missing comment in secret key`。文案里带「password」，**但不是口令问题**。
- **真实成因（2026-10-03 本机 14 组形态逐条复现）**：私钥**取到了空值**。CI 里最常见的三条路径：① 变量配在 **Environment Secrets** 而作业没声明 `environment:`（对作业不可见 → 展开成空串）；② 变量名拼错或配在了另一个仓库/环境；③ 把**文件路径**当私钥全文填了进去（`Invalid symbol 46`），或多包了一层 base64（`Missing encoded key in secret key`）。⚠ 路径形式只对**本机**有意义：`npm run tauri:build` 的注入包装器会把 `TAURI_SIGNING_PRIVATE_KEY` 里放的、确实存在的 `.key` 路径（含 `~/…`）读成内联全文；CI runner 上没有你的 `~/.tauri`，那里必须放**私钥全文**。
- **为什么这么晚才炸**：`bundle.createUpdaterArtifacts: true` 时 tauri 要等整套 Rust 编译跑完、在打包那一步才去解私钥，一次空跑要花十几分钟。
- **处理**：先确认仓库级 **Variables** 两项都在（`release.yml` 读 `vars.`，且**没有**任何私钥前置校验步骤——2026-10-03 用户决定，私钥在位与否由维护者自行确认，因此这类配置错仍要等到打包那一步才暴露）。本侧**也没有** `--check-only` 这类前置自检（该入口已随 2026-10-03 的注入器重写移除，`resolveKey` / `checkKeyShape` / `configuredKeyIds` / `checkPairing` / `classifySignerError` / `dryRunSign` 同样不再存在）：**构建就走 `npm run tauri:build` / `npm run build`，包装器只注入私钥**（不判形态、不试签、配对不符也只告警）。所以要看它打印的几行日志人工核对：每项**来源文件名**（进程环境 / `.env.local` / `.env` / `~/.tauri/wbBridge{,-updater}.env` / 兜底 `.key`；「钥来自环境、口令来自 `.env.local` 里另一把钥」的混搭最难归错）、是否出现「已注入内联签名私钥（来自 …）」、「公钥配对 OK（`2B11F78BEA8A43F`）」，以及产物的 `.sig` 解出的签名者 key ID 是否等于 `plugins.updater.pubkey` 里**唯一生效的第一条**。全程**绝不回显密钥与口令**。完整对照表见 `docs/wiki/版本与发布.md`「签名与自动更新」。
- ⚠ 本机已按 `1.0.2` 构建过（2026-10-03，退出码 0）；安装包名里的版本号随源码版本变化，改动版本后重新构建即得到对应名字。

### 构建时报 `The updater secret key … does not match the public key from plugins > updater > pubkey`

- **含义**：签名用的私钥**不是**配置里那条公钥对应的钥。`plugins.updater.pubkey` 虽然可以塞进多段公钥框，但 `minisign-verify` 的 `PublicKey::decode` 只读解码文本的**前两行**，**只有第一条生效**（`tauri build` 比对的也正是第一条）——"多嵌几条当轮换白名单"是不成立的。
- **后果**：这样签出的 `.sig` 会被客户端**判无效**，不是可以忽略的噪音。
- **处理**：用配置里那条公钥对应的私钥签名，或把 `plugins.updater.pubkey` 换成**真正签名那把**的公钥（当前配置只嵌 `2B11F78BEA8A43F`）。⚠ 换 `pubkey` 属对外契约变更：**已发布的老客户端只认它自己内嵌的那条**，所以换钥那一次发布必须让老版本还能验签升级过去。2026-10-03 本机复跑已确认该告警**消失**。

### 构建时那句 `Warn skipping app notarization, no APPLE_ID & …` 要不要修？

- **不用**：macOS 走 ad-hoc 签名（`bundle.macOS.signingIdentity: "-"`），既没有 Developer ID 证书也没有公证凭据，tauri 因此跳过公证；两个参考项目同样带着这句出货。代价是 `spctl` 会判定 rejected，用户侧按本页「macOS 提示"无法打开"或"已损坏"」的 `xattr` 步骤放行。商用签名/公证的接入位置见[版本与发布](版本与发布)「商业签名与公证」（**尚未接入**）。
- 同理，macOS 27 上跑 `npm run make:dmg` 会看到 `hdiutil … deprecated … use diskutil image` 的告警——**产物正常**，脚本暂时继续用 hdiutil。
