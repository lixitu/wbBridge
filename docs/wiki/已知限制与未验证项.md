# 已知限制与未验证项

本页是本 wiki 的**诚实边界页**。以下内容区分两类：**未验证项**（可能已实现但缺少实测证据）与**已知限制**（明确的、设计上或实现上的边界）。所有条目均来自 `README.md`、`AGENTS.md`、`docs/validation.md`，不做推测。

## 二、已知限制

| # | 限制 | 说明 |
|---|---|---|
| 1 | **免费模型名单、额度与可用性由上游决定** | 本应用不控制也不缓存额度；模型可能随时增减或不可用 |
| 2 | **未做商用代码签名 / 公证** | Windows 可能提示未知发布者；macOS 需按放行说明操作（ad-hoc 签名） |
| 3 | **Windows ARM64 与 Linux 包未实机验证** | 已由 CI 构建并随 Release `v1.0.2` 发布（2026-10-03 完整一轮），但没有在真实 Windows / Linux 机器上装过 |
| 4 | **仅 PAC / SOCKS 代理暂不支持** | 系统代理仅支持 macOS `scutil` / Windows 注册表解析出的手动 HTTP/HTTPS 代理（与原版一致） |
| 5 | **4 个新视图未经 GUI 实机验证** | 侧栏「运行日志 / 用量与额度 / WorkBuddy 集成 / 关于与更新」已实现（含壳命令 `read_log` 与核心 `usage` 计数），但仅经单测 / lint / 构建验证，**从未在 Tauri GUI 中实机点击确认** |
| 6 | **浅色主题 3 处对比度未达标** | 副标题、页脚说明、耗时行仍用 `--muted`，对比度低于 WCAG AA 的 4.5:1（既有问题，尚未处理） |
| 7 | **`cargo fmt --check` 全仓不干净** | **未作为门禁**；代码风格以 clippy 0 warning 为准 |
| 8 | **探测会消耗少量免费额度** | 免费模型检测向每个模型发送简短真实请求 |
| 9 | **单实例锁约束** | `service.pid` 指示进程存活时重复启动会失败（独立进程退出码 2），不会抢占端口 |
| 10 | **版本号值域说明** | 产品版本 1.1.6；核心 crate 版本 1.1.6（2026-10-10 起随产品版本同步，此前 0.1.0 有意解耦——用户指令推翻）；`status.json` 中的 `version` 为历史沿革值 0.2.0（界面上可见），前两者随 `version:set`/`version:check` 统一，`status.json` 值**不得**顺手改 |
| 11 | **仓库提交状态** | 分支 `dev`（远端 `origin = https://github.com/trexwb/wbBridge.git`，另有 `main`），`git ls-files` 有 **103** 个被跟踪文件；v1.0.2 的版本推进与本轮改动**仍在工作区未提交**（提交由用户决定，Agent 不自动 `git commit` / `git push` / `git tag`） |
| 12 | **Node 仅用于前端构建** | Node.js >= 24 **只**服务 Vite 构建与 `scripts/*.mjs`；核心运行不依赖 Node，也不得把 Node 运行期重新引入核心链路 |
| 13 | **v1.0.1 及更早的用户收不到自动更新** | 那一版根本没接线 updater（产物无 `.sig`、面板无更新区），必须由用户手动下载安装包升级一次；从 v1.0.3 → v1.0.4 起更新链路才可能自我生效 |
| 14 | **更新通道受 Draft 闸门控制** | endpoint 指向 `releases/latest/download/latest.json`，而 GitHub 的 `releases/latest` **不含 draft 与 prerelease**——人工点「Publish release」之前，老客户端拿到 404 属预期（draft 即灰度闸门），不是"更新功能坏了" |
| 15 | **面板偏好只持久化两项** | 当前视图、以及「启动后自动检查更新」开关（`src/core/prefs.js`，键前缀 `wb.` + 字段白名单 + 2KB 上限）。详情栏收起状态与窗口尺寸/位置**不持久化**：后者需要 `tauri-plugin-window-state`（新依赖 + 与 `quit_app` 关停时序的交互无法在无 GUI 验证下确认，故未接入）。**注意别混淆**：系统代理开关与 WorkBuddy 配置文件路径由**核心**持久化在数据目录 `settings.json`，与面板 `localStorage` 无关 |
| 16 | **存储里绝不写凭据** | `prefs.js` 的写入路径只接受白名单键、且对值做字段投影（如 `update` 只留 `autoCheck` / `lastCheckedAt`）；`api-key`、`OPENCODE_SERVER_PASSWORD`、models 文件路径等一律进不了 `localStorage`（有对应单测钉住） |
| 17 | **面板状态发布改为帧级合并（2026-10-03 起）** | 壳发来的 `core-status` / `core-activity` / `core-failed` 不再到达即渲染，而是入队后由 `requestAnimationFrame` 每帧最多 flush 一次（无 rAF 环境回落 16ms `setTimeout`）：合并语义与逐个执行等价、最终取值不变，但面板可见状态最多滞后约一帧；排查「面板看起来慢半拍」时先想到这条 |
| 18 | **验签只认 `pubkey` 的第一条公钥** | `plugins.updater.pubkey` 里多嵌几条**不构成**轮换白名单（`minisign-verify` 的 `PublicKey::decode` 只读解码文本前两行，其余静默丢弃）；因此**换签名钥必须同一次发布里同步替换 `pubkey`**，且已发布的老客户端只认它自己内嵌的那条——换钥那一次发布要挑老版本仍能验签升级过去的时机。当前配置只嵌 `2B11F78BEA8A43F` 一条 |
| 19 | **macOS 的 `.dmg` 不经 Tauri** | `bundle.targets` 为显式列表 `["app","nsis","msi","appimage","deb"]`（不含 `dmg`），dmg 由 `npm run make:dmg`（`scripts/make-dmg.sh`，hdiutil）生成；原因是 Tauri 的 create-dmg 末尾要用 AppleScript 美化窗口，无头 runner 上会失败。交叉构建**必须传 `TARGET_TRIPLE`**（否则架构取 `uname -m`＝runner 架构）；macOS 27 上 hdiutil 会打 `deprecated … use diskutil image` 告警，产物正常，暂未改造 |

## 三、不该被描述为"已实现"的事

为避免文档与界面口径失真，以下内容**严禁**在其他页面或对外说明中被当作已完成功能：

- ❌ 宣称 4 个新视图（运行日志 / 用量与额度 / WorkBuddy 集成 / 关于与更新）与更新区已经 GUI 实机验证；
- ❌ 宣称 GUI / 托盘 / 窗口行为已实机验证；
- ❌ 宣称 `latest.json` 已经可用、或宣称除 **macOS aarch64 dmg** 之外的平台安装包只停在"待 CI 产出"（2026-10-03 完整一轮已把六平台产物 + `.sig` + 清单发到 Release `v1.0.2` 上）；**但仍不得宣称更新清单可用**——那一轮的六条 `url` 因 GitHub 把资产名空格规范化成 `.` 而全部 404，脚本与 CI 闸门已修，**线上那份清单仍坏着、新闸门本身还没在 CI 实跑过**；
- ❌ 宣称「自动更新已端到端可用」（真实的一次 检查→下载→安装→重启 尚未做过），或引导用户自行生成签名私钥（wbBridge 专用钥已由维护者生成并内嵌公钥，换钥必须同步换 `pubkey`，且只有 `pubkey` 第一条生效）；同样不得把"产出了 `.sig`、CI 全绿"当成客户端验签通过——`with-updater-key.mjs` 是 `npm run tauri:build` 的**注入包装器**（不判形态、不试签、配对不符只告警），本地产出 `.sig` 只证明**钥 + 口令能用、key ID 与配置一致**，不证明产物已被客户端验签；
- ❌ 把 `status.json` 中的 `0.2.0` 当作产品版本；
- ❌ 宣称已支持 PAC / SOCKS 代理；
- ❌ 宣称接入了商业代码签名或 Apple 公证（A7 只是把**接入位置与所需变量**写进文档，配置里没有这些键）；
- ❌ 宣称「更新失败后的一次真实回滚」已走过，或宣称 `localStorage` 偏好已在真实 WebView 里验证过。

## 四、如何把这些边界用起来

- 提交 / 发布前，请对照[版本与发布](版本与发布)的「发布前检查清单」，其中「实机启动 GUI」仍未完成，「产出安装包」本机只有 macOS aarch64 的 dmg 落地（其余五平台已由 2026-10-03 的 CI 完整一轮产出并随 Release `v1.0.2` 发布，但都没实机装过），且**推标签之前必须先确认 GitHub 仓库级 Variables 已配好签名私钥全文与非空口令**（缺任一项会在一整套 Rust 编译跑完后的打包那一步报 `Missing comment in secret key`，2026-10-03 首轮 CI 正是栽在这里）。CI 与本地都**没有**私钥前置校验这一步：构建直接走 `npm run tauri:build` / `npm run build`，包装器只注入私钥（不判形态、不试签、配对不符只告警），所以要人工核对它打印的来源与 `.sig` 的 key ID 是否等于 `plugins.updater.pubkey` 里那条；同时遵守「先版本推进提交、再在该提交上打标签」的顺序。
- 排查问题时，先确认自己处在哪种运行形态（见[常见问题与故障排查](常见问题与故障排查)）。
- 若在新环境中完成了上述任一未验证项，应在 `docs/validation.md` 追加记录，并同步更新本页与 `README.md`。
