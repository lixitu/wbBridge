- ❌ 宣称「同步失败还能自动回滚到上一份配置」（当前版本**完全不写备份**，兜底只有原子替换 + 文件锁 + 写前二次读取），或宣称补建出来的空 `models.json` 已被插件自身成功读入；
- ❌ 宣称平台聚合发现、`Provider.models` 权威清单或上游失败中文文案在**真实 GUI** 链路下跑通过（三者的证据层级各不相同：文案判定与清单过滤只有单测 + 本机沙箱；`modelscope` 那份 9 条清单确实拿**真实 Key 的命令行请求**逐条校过——4 条「在册但打不通」就是这么削掉的——但那不等于「保存 → 热生效 → 探测通过 → 在插件里真实对话」这条 GUI 端到端链走过）；
- ❌ 宣称「发布说明会随更新清单推送给用户」（`latest.json` 没有 `notes` 字段，Release 正文是硬编码一句 + `generate_release_notes` 自动补，`RELEASE-NOTES-v*.md` 只是人工粘贴的底本），或宣称线上 Release 正文与仓库底本一致（`v1.1.10` 的 Release 已 Publish、23 个资产，但正文由维护者**手工粘贴**，与 `docs/version/RELEASE-NOTES-v1.1.10.md` 是否逐字一致属人工核对项——`latest.json` 没有 `notes` 字段，CI 也不会替你同步）。

## 四、如何把这些边界用起来

- 提交 / 发布前，请对照[版本与发布](版本与发布)的「发布前检查清单」，其中「实机启动 GUI」仍未完成，「产出安装包」本机只有 macOS aarch64 的 dmg 落地（其余五平台已由 2026-10-03 与 2026-10-10 两轮 CI 完整跑完，分别随 Release `v1.0.2`、`v1.1.10` 各发布过一次 23 资产，但**两轮六个包都没实机装过**，本机也从未构建过 1.1.10 的包），且**推标签之前必须先确认 GitHub 仓库级 Variables 已配好签名私钥全文与非空口令**（缺任一项会在一整套 Rust 编译跑完后的打包那一步报 `Missing comment in secret key`，2026-10-03 首轮 CI 正是栽在这里）。CI 与本地都**没有**私钥前置校验这一步：构建直接走 `npm run tauri:build` / `npm run build`，包装器只注入私钥（不判形态、不试签、配对不符只告警），所以要人工核对它打印的来源与 `.sig` 的 key ID 是否等于 `plugins.updater.pubkey` 里那条；同时遵守「先版本推进提交、再在该提交上打标签」的顺序。
- 排查问题时，先确认自己处在哪种运行形态（见[常见问题与故障排查](常见问题与故障排查)）。
- 若在新环境中完成了上述任一未验证项，应在 `docs/validation.md` 追加记录，并同步更新本页与 `README.md`。
