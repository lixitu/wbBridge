# 快速开始

本页说明安装、首次运行、模型读取与检测、导入 WorkBuddy 的完整流程。

> 本页所有命令与路径均取自仓库真实配置（`README.md`、`package.json`、`src-tauri/tauri.conf.json`、`AGENTS.md`、`docs/contract.md`）。标注「未验证」的能力请勿当作已可用。

---

## 1. 前置条件

| 依赖 | 要求 | 说明 |
|---|---|---|
| WorkBuddy | 先安装并登录 | WB Bridge 只为 WorkBuddy 服务；它需要一个已存在的 `models.json` 作为导入目标 |
| OpenCode 运行时 | **无需预装** | 应用会优先复用本机 `opencode`，找不到则自动从 npm registry 下载（详见[核心概念与功能](核心概念与功能)） |
| 操作系统 | macOS 10.15+ / Windows 10、11 / Linux x64 | 见下方安装状态表 |
| Node.js | **>= 24**（仅从源码构建时需要） | 核心运行**不依赖** Node；Node 只用于 Vite 构建面板与仓库根的 `scripts/*.mjs` 脚本 |
| Rust | stable，`rust-version` 两侧统一声明 **"1.90"** | `src-tauri/Cargo.toml`（壳）与 `src-tauri/core/Cargo.toml`（核心）均写 1.90：壳侧下限来自锁定依赖（tauri 2.12 / tauri-runtime-wry / tray-icon 与各官方插件都声明 1.90），核心自身下限是 1.88（`icu_*` ← `idna` ← `url` ← `reqwest`），取最大值。CI 四个作业一律用 `dtolnay/rust-toolchain@stable`。⚠ **未验证**：本机只有一个工具链（`rustc 1.98.1`），**没真的在 1.90 上构建过**，1.90 是读锁定依赖声明取最大值得来的结论 |

终端里用 `node -v` 确认版本；若由 nvm 管理，非登录 shell 的 PATH 中可能没有 `node`，先执行：

```sh
export NVM_DIR="$HOME/.nvm"; . "$NVM_DIR/nvm.sh"
```

>
> 说明：`bundle.targets` 是显式列表 `["app", "nsis", "msi", "appimage", "deb"]`（**不含 `dmg`**），macOS 的 `.dmg` 由 `npm run make:dmg`（`scripts/make-dmg.sh`，hdiutil）在 `npm run build` 链尾生成，非 macOS 平台自动跳过；CI 矩阵覆盖 macOS ARM/Intel、Windows x64/ARM、Linux x64/ARM 共六组目标（交叉构建必须传 `TARGET_TRIPLE`，否则 dmg 会拿错架构）；macOS 构建产物**未做签名/公证**，构建期 `Warn skipping app notarization, …` 属预期告警。

### macOS 首次打开（ad-hoc 签名放行）

应用使用 **ad-hoc 签名，未做 Apple 公证**。首次打开若被系统拦截：

1. 先尝试打开；
2. 到「系统设置 → 隐私与安全性」点击「仍要打开」；
3. 若提示「已损坏」（来源可信的前提下），执行：

```sh
xattr -dr com.apple.quarantine "/Applications/WB Bridge.app"
```

Windows 可能提示「未知发布者」（未做商用代码签名），属预期行为。

## 3. 首次运行会发生什么

应用启动后（壳在自己的专用 tokio 运行时上装配核心，两者同一进程），核心按固定时序推进。按 `src-tauri/core/src/orchestration.rs` 的启动时序：

1. **端口校验与数据目录准备**——端口须在 1024–65535 之间；数据目录 `create_dir_all` 并设为 `0700`。
2. **单实例锁**——读取 `service.pid`；若指向仍存活的进程即视为已在运行，独立进程会以退出码 2 结束，**不会抢占端口**。⚠ 锁里的 pid 只要「> 0、不是自己、且仍被系统认作存活进程」就判冲突，因此**退出码 2 与有没有填平台 Key 没有因果关系**（这一步完全不读 `providers.json`）；Windows 上偶发的反复退出码 2（残锁 / 安装版与调试版共用同一数据目录 / `relaunch()` 抢锁）**当前未取证、未修**，临时恢复办法见[常见问题与故障排查](常见问题与故障排查)。
3. **生成/读取 `api-key`**——缺失时生成 32 字节随机 hex，文件权限 `0600`。这是后续所有 HTTP 请求的 Bearer 令牌。
4. **读取设置与上一份状态**——`settings.json`（容错解析）、上一份 `status.json`（延续模型检测结果）；`opencode.log` 超过 5MB 时轮转。上一轮的目录与通过集可用时，启动会**直接沿用**上轮结果并按当前端点重发一次发布配置，不再自动全量重读+重检。
5. **解析 WorkBuddy 配置文件路径**——按 `BUDDY_MODELS_FILE` → 已保存值 → 自动发现的顺序；**显式位置失效即返回空，绝不静默回退到猜测路径、也绝不补建文件**。自动发现分支有一种例外：插件目录已存在但 `models.json` 缺失时，会**补建一个内容为空数组的空配置**（文件已存在绝不改写；父目录不存在绝不建目录——那等于插件没装；任何 IO 失败静默返回，不会把「补建失败」说成「已安装」）。CodeBuddy 侧是同款的对称实现。
6. **定位或下载 OpenCode 运行时**，然后启动 OpenCode 子进程，axum HTTP 服务开始监听。⚠ 安装后与启动前的 `<file> --version` 回读各带 **15 秒**预算，**只有超时才重试一次**（退出码非 0 / 不可执行不重试），两次都超时才会给出中文说明——本机 CPU/磁盘被占满时最容易撞上，等空下来点面板状态条上的「重试」即可。
7. **`/agent` 校验**——确认隔离配置里的 `buddy-bridge`、`buddy-chat` 两个自定义 agent 存在，否则服务阶段不会进入 `ready`。
8. **系统代理**（若开关为开）——解析系统代理并注入子进程环境；**解析失败回退为关闭，不阻断启动**。
9. **启动导入**——先清除旧的自身条目，再**逐模型真实探测**（每个模型 60 秒预算），仅通过探测的模型进入发布集。
10. **发布到 WorkBuddy**——把发布集写入 `models.json`（原子写 + 增量合并，只动自己名下的条目），随后进入后台轮询与刷新。

首次运行会**按需下载 OpenCode 运行时**（大约几十 MB）并**消耗少量免费额度**用于探测，属正常现象。

## 4. 模型读取与检测

界面上的三个相关入口：

| 入口 | 位置 | 行为 |
|---|---|---|
| **重新读取免费模型** | 主区操作区 | 重新读取免费模型目录（含重启运行时） |
| **检测全部模型** | 主区操作区 | 对全部模型发起真实探测；也可对单个模型单独触发检测 |
| **导入 WorkBuddy** | 指标卡右侧插槽 | 把当前可用模型发布到 WorkBuddy 的 `models.json` |

流程与判定：

- **发现**：读 OpenCode 侧的模型目录并按免费判定筛选（输入 / 输出 / 缓存价格全为 0、输出支持文本、非 deprecated）。范围是**聚合发现**：官方 OpenCode 免费目录 + 已在侧栏「平台」里配过 Key 的平台，**条数随上游目录与平台清单变化**（多平台接入前那次独立冒烟刷新到 8 个，只是当时的实测值，不是固定数）；某一家平台读取失败不会丢掉其他平台的目录。注册表里若某平台带**权威模型清单**（当前 `modelscope` 为 9 条），注入与发现都只认这份清单，不再用 models.dev 的 catalog 声明。
- **探测**：向每个模型发送简短真实请求，区分为「工具调用类」与「纯文本类」两类探测；单模型 60 秒预算，该模型的重试共用同一 deadline（最多重试 1 次）。
- **发布**：只有探测通过（`ok`）的模型会进入发布集。它们在 `/v1/models`、插件配置与用量统计里的**客户端 ID** 形如 `<前缀> · <名称>`——注册表平台用其 `label`（`ModelScope · …` / `智谱 · …` / `腾讯混元 TokenHub · …` / `SiliconFlow · …`），`opencode` 与未注册命名空间一律回落 `OC`。⚠ 面板的模型行**不显示这个 ID**，显示的是内部全限定 id（`<命名空间>/<目录 key>`，如 `opencode/big-pickle`），两者区别见[使用指南](使用指南)。

指标卡上会同时显示三个数字：**已发现**、**可用**、**待检测**。

> ⚠ 探测会真实调用模型，**会消耗少量免费额度**；额度与可用性由上游 OpenCode 决定，本应用不控制也不缓存额度。

每个模型行会以徽章形式展示能力与状态，含义见[使用指南 § 模型状态与徽章含义](使用指南)。

## 5. 导入 WorkBuddy

1. **自动导入**：启动流程中，若成功解析到 WorkBuddy 配置且探测完成，会把通过探测的模型自动写入。
2. **手动导入**：点主区的「导入 WorkBuddy」按钮，在弹出的文件选择器里选中 WorkBuddy 的 `models.json`（通常在 `~/.workbuddy/models.json`，macOS / Linux 默认值）。
3. **更换位置（Windows）**：Windows 下走「已保存值 → 自动发现」流程；也可用**托盘菜单的「选择 WorkBuddy 配置…」**重新指定。
4. **写入规则**：只新增 / 更新 / 清理**本应用自己名下**（`OWNER = 'buddy-bridge-v1'`）的条目，用户手动配置的条目与对象元数据**原样保留**；全程原子替换（文件锁 + 写前二次读取 + 同目录临时文件再 `rename`），**不再往你的配置目录里写 `.bak` 备份**（旧版本攒下的那些会在下一次同步时按同族白名单自动清掉，你自己命名的 `*.bak` 不受影响）。⚠ 如实提示：因此配置真被写坏时**没有自动回滚点**，兜底只有上述原子写入本身；重要配置请自行留一份副本。
5. **退出清理**：**关闭窗口即退出应用**（全平台一致），也可用托盘「退出 WB Bridge」；两条路径相同 —— 核心优雅停止服务并完成 WorkBuddy 配置清理（移除自己名下的条目，保留用户其他配置）。

导入 / 切换配置文件时会弹出系统文件选择器；若你点了「取消」，不会有状态变更。操作结果会出现在面板的**反馈条**（成功为绿色、错误为橙色，并带 `aria-live` 播报），三种文案为：

- 取消：`已取消导入，配置未更改。`
- 无变化：`配置已是最新，共 <N> 个模型，无需重复写入。`
- 成功：`导入完成，已将 <N> 个可用模型导入 WorkBuddy。`

> ⚠ 检测完成后并**不会**自动重新写入 WorkBuddy——需要再点一次「导入 WorkBuddy」才会更新（页脚会提示「已导入 N 个模型 · 再次检测后需点击导入 WorkBuddy 更新」）。

## 6. 数据目录在哪

**两种运行形态的数据目录不同，排查时不要混用**：

| 运行形态 | 数据目录（`api-key` / `status.json` 所在处） | 端口 |
|---|---|---|
| 桌面应用（正式形态） | Tauri `app_data_dir`：macOS `~/Library/Application Support/app.wbbridge.desktop`（identifier `app.wbbridge.desktop`） | 默认 41980，被占用时由系统分配空闲端口，**以同目录 `status.json` 的 `endpoint` 为准** |
| 独立核心二进制 | macOS `~/Library/Application Support/Buddy Bridge`、Windows `%APPDATA%\Buddy Bridge`、Linux `${XDG_CONFIG_HOME:-~/.config}/Buddy Bridge`（可用 `BUDDY_DATA_DIR` 覆盖） | `BUDDY_PORT`，默认 41980 |

健康检查（`/health` **同样需要 Bearer 鉴权**，无 key 返回 401）：

```sh
curl -H "Authorization: Bearer $(cat "$HOME/Library/Application Support/Buddy Bridge/api-key")" \
     http://127.0.0.1:41980/health
```

列出已发布的模型（客户端可见模型）：

```sh
curl -H "Authorization: Bearer <key>" http://127.0.0.1:41980/v1/models
```
