# 核心概念与功能

本页解释 WB Bridge 的四条主线：运行时隔离托管、免费模型发现与真实探测、OpenAI 兼容接口、模型配置合并写入。所有描述均可在 `src-tauri/core/src/` 源码中直接核对。

---

## 1. 运行时隔离托管

### 1.1 它解决什么

WorkBuddy 只接受 OpenAI 兼容的模型清单与接口，而免费模型在上游 OpenCode 侧动态变化、且额度不可查询。WB Bridge 的做法是：**在本地拉起一个被完全隔离的 OpenCode 运行时**，由它承担真实模型推理，再把结果翻译成 WorkBuddy 能懂的 OpenAI 格式。

隔离的意义在于：**不污染用户自己的 OpenCode 配置、登录态和其他 provider 的密钥**。

### 1.2 定位与获取运行时（`runtime.rs`）

1. **优先复用本机已有的 OpenCode**：扫描候选后与官方 `latest` 版本号比较，本机版本不低于官方就直接使用（会写入日志说明来源与版本）。
2. **否则下载官方 runtime**：从 npm registry 取 `latest` 元数据与 tarball 并安装。

供应链红线（全部保留）：

- registry 走**白名单**；
- tarball 的 `sha512-` 完整性**必须校验通过**；
- 只取 `package/bin/<binary>` **单个成员**，不整包解压；
- 安装后**回读 `--version`** 确认可执行；
- **拒绝 `.cmd` / `.bat` / `.ps1` 启动器脚本**。

若读取官方版本元数据失败，但本机存在可用候选，则退回使用本机版本并记录原因；两者都没有才报错。

### 1.3 隔离配置（`isolated_config()`）

注入给 OpenCode 的配置固定为：

| 项 | 值 |
|---|---|
| `permission` | 全部原生权限按 ask / deny 生成（`native_permissions()`） |
| `autoupdate` | `false` |
| `share` | `disabled` |
| `agent.buddy-chat` | `mode: primary`，纯文本外部对话；提示词明确「不做工具调用、不声称执行过动作」 |
| `agent.buddy-bridge` | `mode: primary`，只作为外部助手的推理组件；提示词明确「绝不调用 OpenCode 原生工具，外部工具调用只在 JSON 响应里描述，执行权属于外部客户端」 |

启动后核心会请求 `/agent` 校验 **`buddy-bridge` 是否存在**——因为这是隔离运行时自带的审批 agent，而不是用户自己的构建 agent；缺失则报 `Dedicated approval-gated agent missing`，服务不会进入可用状态。

### 1.4 子进程环境隔离

子进程环境先 `env_clear()`，再**只**注入白名单变量：

```
PATH, HOME, USER, LANG, TMPDIR, SHELL, SSL_CERT_FILE, NODE_EXTRA_CA_CERTS,
SystemRoot, WINDIR, TEMP, TMP, USERPROFILE, APPDATA, LOCALAPPDATA, PATHEXT, COMSPEC
```

其余变量一律不透传，尤其**其他 provider 的 API Key 与 OpenCode 登录态**。此外还会注入 XDG 隔离路径、代理环境变量与 `OPENCODE_*` 覆盖项，并设置服务密码（由两个 UUIDv4 截断为 48 个 hex 字符，随机熵 ≥ 122×2 bit）。

### 1.5 生命监护

- **父进程看门狗**：子进程带 `BUDDY_PARENT_PID`，父进程消失后自行优雅退出，避免留下占端口的孤儿进程。
- **探活**：对 `GET /global/health` 发起 1 秒超时的健康请求。
- **日志**：OpenCode 输出追加进数据目录下的 `opencode.log`；超过 **5MB** 时轮转。

## 2. 免费模型发现与真实探测

### 2.1 发现：什么算「免费」（`backend.rs::free_models`）

核心从 OpenCode 的 provider 列表里取 `id == "opencode"` 那一个，**逐条**满足以下条件才收录：

| 条件 | 判据 |
|---|---|
| 输入免费 | `cost.input == 0` |
| 输出免费 | `cost.output == 0` |
| 缓存读免费 | `cost.cache.read == 0`（`null` / 缺失按 `0` 处理） |
| 缓存写免费 | `cost.cache.write == 0`（同上） |
| 支持文本输出 | `capabilities.output.text !== false` |
| 未下线 | `status !== "deprecated"` |

每个收录模型会带出 `context` / `input` / `output`（来自 `limit.*`）、`images`、`toolcall`、`reasoning`、`variants` 等字段，内部 ID 形如 `opencode/<key>`，最后按 ID 排序。

> 找不到该命名空间的 provider 时核心会**报错 `OpenCode provider missing`**，而不是静默返回空列表——这样面板上不会出现「一切正常但没有模型」的假象。

### 2.1b 多平台聚合发现与「权威清单」（1.1.x 起）

上面那六条判据（CostZero）**只有一份实现**：`backend.rs::free_models_in(providers, namespace)`。它被调用两类命名空间：

- **`opencode`**：OpenCode 自带的免费模型，无需任何 Key，判定与文案与接入多平台之前逐字节一致；
- **每个已配 Key 的注册表平台**（`modelscope` / `siliconflow-cn` / `tencent-tokenhub` / `zhipuai`，见 `providers.rs::PROVIDERS`）：`Backend::models()` 逐个平台聚合发现，**单平台失败只记日志、不丢其他平台**的目录。

平台的 Key 只经 `OPENCODE_CONFIG_CONTENT` 注入最小声明段（`runtime.rs::providers_section_for`），**绝不进子进程环境变量白名单**。

**「权威清单」是这一节最容易误解的地方**（`providers.rs::Provider.models` / `served_models`）：

| 情形 | 行为 |
|---|---|
| `models` **非空**（今天只有 `modelscope`，9 条） | 这份清单**替代** models.dev 的目录声明：注入段只写清单里的条目，发现阶段也只放行清单里的 key |
| `models` **为空**（其余三家 + `opencode` + 未知命名空间） | 沿用目录声明，注入段带锚点占位条目 `wbbridge-provider-anchor`（`runtime::ANCHOR_MODEL_KEY`，发现阶段按保留名过滤，不是真模型） |

由来是实测到的落差：ModelScope 的免费推理网关实际在册的 id 与 models.dev 声明的 7 个「免费」**交集为空**，而 OpenCode 把注入段与目录**合并**而不是替换——只声明不够，不过滤的话探测队列里依旧是对方不承接的那批过期 id，全部以一句 `has no provider supported` 失败。

> 🔴 两点如实边界：① 清单里 `cost: 0` 是**本工具的主动声明**（免费判定依赖它），依据是对方公开的「每日提供 2000 次免费 API 调用额度」口径，不是对方接口回显的字段；② 清单**随版本发布、不做远程拉取**，上游新增免费模型不会自动出现。这 9 条在真实 Key 下的逐条探测通过率、发布后的真实对话表现都**未系统验证**（见[已知限制与未验证项](已知限制与未验证项)）。

### 2.2 探测：为什么必须真打一次（`probe.rs`）

「免费」只说明价格，不说明这个模型**能不能被 WorkBuddy 真正驱动**。所以核心会对每个模型发一次**真实请求**：

- 请求体携带 5 个工具（`Read`、`Write`、`Bash`、`Glob`、`WebSearch`）与 `parallel_tool_calls: false`，模拟真实 WorkBuddy 流量；
- 用户消息为 `Read /external/probe-<token>.txt and report its contents.`，`token` 是每次不同的 16 位十六进制随机串；
- **判定通过的条件很严格**：响应里**恰好 1 个** tool call、名称为 `Read`、且参数 `file_path` 包含本次 token；
- 不满足时给出 `no_action`（完全没产生动作）或 `probe_mismatch`（动作不符）两类判定失败码。

### 2.3 超时、重试与降级

| 规则 | 说明 |
|---|---|
| 单模型预算 | **60 秒**（`PROBE_TIMEOUT_MS`），每个模型各持一份 |
| 重试 | 仅对**语义误判**重试一次，且与首次尝试**共用同一个 deadline**，不重新计时 |
| 不重试的情形 | 格式类失败、超时 |
| 格式类失败 | 降级为 `chatOnly`（导入后仅支持普通对话），仍可能进入发布集 |
| 执行类失败 | 直接判定失败，不发布 |

> ⚠ 降级为 `chatOnly` 有**两条入口**，此前只有第一条：① 目录声明 `capabilities.toolcall == false` 的模型走 `invalid_tool_call`；② 上游明说「该模型不支持函数/工具调用」（`probe.rs::tool_call_unsupported`）——**声明为真、平台实际不给调用**时就是这一条，此前它被 `to_bridge_error` 归到 `model_error`/`upstream_error`，等于**把一个能正常对话的模型整个丢弃**。两条现在都汇到同一次 `chat_only_attempt`（真实纯对话请求），通了才按 `chat_only` 发布并在面板注记原因；**兜底那次纯对话请求也以同一理由被拒时同样按 `chat_only` 发布**（主探测与兜底指向同一结论），只有兜底报**别的**错（鉴权 / 404 / 限流）才照旧记失败。判定刻意收紧，且这类失败**不重试**。

**上游英文报错的中文说明只有一个漏斗**：`probe.rs::probe_failure` 在**未超时**分支上改写文案，`code` / `status` 逐字保留、都不触发重试、不撤销其它已发布模型。目前四类：地区拒绝（`region_unavailable_message`，按出口 IP 的国家拒绝，唯一可操作入口是侧栏「运行设置 → 使用系统代理」——终端里 `export https_proxy` 不会透传给子进程）、提供方撤架（`deprecated_model_message`）、该平台网关不承接此 id（`unserved_model_message`）、以及「条目在册但这把 Key 没访问权」（`unknown_service_id_message`，按措辞分两支）。判定都收紧到「被拒词 + 主语/地区/弃用词」同时在场且间隔受限，`429`、`invalid api key`、`context length exceeded` 等逐条断言**不得**被说成上述任一类。

> 探测会真实消耗少量免费额度；**剩余额度无法查询**（上游 provider 未提供可靠的余额 API），核心只能按错误文本与状态码归类失败原因。

### 2.4 观测 ≠ 判定

运行期记录的模型状态是**观测结果**（本次调用产生几个动作、拦截了几次本地执行尝试、是否发生移交、是否触发格式兜底），而**能力标签只来自探测**。两者在界面上的呈现方式见[使用指南 § 模型状态与徽章含义](使用指南)。

## 3. OpenAI 兼容接口

### 3.1 路由与鉴权（`server.rs`）

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/health` | 健康检查（**同样需要鉴权**） |
| `GET` | `/v1/models` | 列出当前可用（已发布）模型 |
| `POST` | `/v1/chat/completions` | 对话补全，支持 SSE 流式 |
| `POST` | `/admin/probe` | 触发探测（可带 `model` 只探一个） |
| `POST` | `/admin/system-proxy` | 切换系统代理（`{ enabled }`） |
| `POST` | `/admin/import` | 导入 WorkBuddy 配置（`modelsFile`） |
| `POST` | `/admin/refresh` | 重新读取模型（不读请求体） |
| `POST` | `/admin/shutdown` | 优雅关停（先响应、再触发） |
| `POST` | `/admin/provider-status` | 四平台的 `{ id, label, configured }`（不读请求体、不回任何 Key） |
| `POST` | `/admin/set-provider-key` | 写入用户自持平台 Key 到 `providers.json`（`0600`） |
| `POST` | `/admin/clear-provider-key` | 删除指定平台的 Key（幂等） |

`ACTION_ROUTES` 的**顺序**先与原实现保持一致（probe → system-proxy → import → refresh → shutdown），2026-10-03 多平台接入的三条 `provider-*` **追加在尾部**（顺序是壳侧契约测试逐项比较的基础之一，不得插入中间）。

鉴权与边界：

- 请求头必须是 `Authorization: Bearer <key>`，缺失或不匹配返回 **401**；校验使用**常量时间比较**；
- 带浏览器 `Origin` 的请求**一律 403**；
- 请求体上限 **8 MB**（超出 413），非法 JSON 返回 400；
- `/v1/chat/completions` **并发上限 8**（含自身；2026-10-10 由用户裁定从 4 调到 8），超出返回 429 `busy`；
- 请求体接收超时 **20 秒**。

### 3.2 模型标识

客户端可见的模型 ID 形如 **`<前缀> · <模型名>`**（`model_status.rs::client_model_id()`）：注册表平台用其 `label`（`ModelScope · …` / `智谱 · …` / `腾讯混元 TokenHub · …` / `SiliconFlow · …`），`opencode` 与不在注册表里的命名空间**一律回落历史前缀 `OC`**（`model_status.rs` 的单测逐条钉死这四种形态）。这个 ID 出现在 `/v1/models`、发布给 WorkBuddy / CodeBuddy 的配置以及用量统计里。⚠ **它和界面列表显示的不是同一个值**——面板 `components/ModelRow.vue:63` 渲染的是该模型对象的 `id`，即**内部全限定 id**（`<命名空间>/<目录 key>`，如 `opencode/big-pickle`、`modelscope/MiniMax/MiniMax-M1-80k`）。请求一个不在可用集合里的模型会得到：

```json
{ "error": { "message": "Select an available free model from /v1/models",
             "type": "model_not_found", "code": "model_not_found" } }
```

### 3.2b `WB · auto` 合成模型名（v1.1.14 落地、v1.1.15 起写入插件配置，端到端未实测）

除真实模型外，`/v1/models` 在**可用池非空时**会在末尾多一条固定条目：

```json
{ "id": "WB · auto", "object": "model", "owned_by": "opencode", "name": "WB · auto" }
```

它**不是一个模型**，是一把路由：请求把 `model` 填成 `WB · auto` 时，核心在同一次可用池快照里按**请求内容**选出一个真实模型，再把 `body["model"]` 改写成它的**全限定 id**（如 `modelscope/Qwen/Qwen3-8B`）。池为空时这条条目**不出现**——不给客户端一个「点了必失败」的入口。

选择规则（`src-tauri/core/src/auto.rs`，纯函数、无 IO）：

| 请求内容 | 候选集 |
|---|---|
| 带图片（`image_url` 内容块） | 只看该模型的 `images` 能力 |
| 带工具定义（`tools` 非空数组） | 排除「仅对话」模型，且要求 `toolcall` |
| 两者都有 | 两个条件同时满足 |
| 纯文本 | 整个可用池 |

某一级候选为空时**退回全池**；退回后仍不合规的请求由既有的模型校验给出 400（不静默换通道）。同级内随机选取，用的是核心已有的 `protocol::random_uuid()` 取模——**没有为此引入随机数依赖**。

三条必须如实理解的语义：

- **响应里的 `model` 字段与用量统计的键都是实际模型的全限定 id**，不是 `WB · auto`。改写发生在核心**首次取读记账键之前**，因此用量页不会出现「WB · auto」这一行——这是设计而非缺陷；
- **失败即摘除**是**既有链路的行为**（不是本功能新增的代码）：真实请求里该模型报受限 / 超时 / 不可用，`record()` 会把它从「已校验」集合摘掉并重算可用模型数与逐模型状态，`/v1/models`、`status.json` 与面板行随之一致。**四类格式性失败不摘除**（输出截断、信封格式、原生工具越权、工具调用格式）；**客户端取消、429、请求体读取超时 408、模型校验的本地 400 都在记账之前结束，因此也不摘除**；
- **被摘除的模型不会自动回来**：恢复要靠面板的「重新检测」或「刷新」，插件配置要等**下一轮同步**才收敛（`record()` 不调 `sync_published`）。

边界不变：仅回环监听、所有路由都要 Bearer 鉴权、任何非空 `Origin` → 403、并发 ≤8、请求体 ≤8MB。所以 CLI / 桌面 agent 直连可用，浏览器内嵌 `fetch` 仍然不行。🔴 **该功能至今没有发过一次真实请求**，全部证据是注入假后端上的单测（见[已知限制与未验证项](已知限制与未验证项)第 20 条）。

### 3.2c 它现在也是插件里的一个条目（v1.1.15）

v1.1.14 的裁定是「`WB · auto` 绝不写进 WorkBuddy / CodeBuddy 的 `models.json`」，用户实测后推翻（「肯定要把 WB · auto 写到插件配置，不然谁都不知道如何使用」）。现在的行为：

- **发布集非空时**，`WB · auto` 作为本工具名下的**一条独立条目**写进两个插件的 `models.json`，排在逐模型条目**之后**（与 `/v1/models` 的末位追加同口径），同时也进该文档的可用模型列表——插件的模型选择器里因此直接挑得到。
- **保守声明**（能力字段宁少勿多）：`supportsImages` 恒为 `false`；`maxInputTokens` 取池内**最小**上下文（每次同步重算，池里没有数值就不写这个键）；不写 `reasoning` / `maxOutputTokens`；`vendor` = `Custom`，`url` / `apiKey` / `buddyBridgeOwner` 与逐模型条目同源。
- `supportsToolCall` **不是固定值**，而是「池里是否存在能接工具调用的候选」（`auto::any_tool_capable`，与核心选档共用同一个档位谓词）。⚠ 这比维护者选定的「保守声明」更收紧一步：只有 `chatOnly` 模型的池里如果声明 `true`，插件侧的工具请求会恒定落到退化档再被校验拒成 400。
- **不计入「同步数量」**：`sync.count` 与 `sync.targets.<目标>.count` 仍只数真实模型（`owned_count` 显式排除别名），`status.json` 的模型列表也不含它，面板不会因此多出一行。
- 归属与清理规则完全沿用既有的：只动 `OWNER = 'buddy-bridge-v1'` 名下条目；用户手动建了同名 `id` 的条目时**不覆盖**，本工具直接放弃写这一条；发布集为空（或退出清理）时这一条被一并删掉。
- 🔴 **插件能否识别并按它发请求，从未实机验证**——别名落盘只在临时目录沙箱里证明过形态。
- 名字口径：对外唯一字面量是 `WB · auto`（空格 + `·` + 空格，与 `OC · 名称` 同形）；该 `id` **刻意绕过** `client_model_id`（走进去会变成 `OC · WB · auto`，与 `chat()` 的字面比较永不匹配）。`WB.auto` 这个旧写法**不再被任何入口接受**，改名的前提是 `1.1.11~1.1.15` 从未构建、从未打标签。

### 3.3 流式（SSE）行为

- 在模型返回之前，先写一帧校验注释：`: validating model response before emission`；
- 每 **10 秒**写一帧心跳 `: waiting`；
- 模型首个进度到达时写 `streamStart` 帧；
- 内容帧经**校验后**再输出（不让格式不合规的内容直接流向 WorkBuddy）；
- 结尾为 `data: [DONE]`；
- 内部使用容量 1024 的有界通道做背压，不会无限堆积。

错误统一为 `{ error: { message, type, code } }`，`type` / `code` 缺省为 `upstream_error`；超时错误的文案统一改写为 `Model request timed out`。

### 3.4 关键设计：执行权永远属于 WorkBuddy

这是整个桥接逻辑里最容易误解的一点：

- **WorkBuddy 随每个请求发来的工具列表才是权威**。桥接不发明工具，也不替模型执行动作。
- 当模型（在 OpenCode 内）试图本地执行时，这个尝试会**被拦下**，并被**翻译成一次外部工具调用**交给 WorkBuddy（`handoff.rs`）。理由很直接：让模型「复述」它想做的事，恰好是模型最容易失败的步骤，还会多花一整轮上游开销。
- 移交时**只填目标 schema 里确实存在的键**，且每个 required 键都必须可满足；否则不产生移交，退回**纠正式拒绝**。
- 映射表覆盖常见工具类别（如 `bash`/`shell` → `Bash`/`PowerShell`，`read` → `Read`，参数 `filePath`/`file_path`/`path` → `file_path` 等），并允许同一原生字段有多个可接受拼写。

### 3.5 格式兜底（`repair.rs`）

当模型返回的 JSON 不合规或工具名/参数名不匹配时，会触发一次**有界**的修复：

- 修复只是**提议**一次翻译，执行权仍完全属于外部客户端；
- **不截断可执行材料**（历史上真实的 `Write` 正文超过 46K 字符，截断会造成内容被替换成 `[object]`）；
- 提取 JSON 时取**第一个括号平衡的对象**，并正确处理字符串内的转义；
- 只有语义等价的别名才给「兜底说明」，**工具的真实定义永远优先**；
- 无法表达时返回 `{"unrepairable": true}`，交回原模型处理下一步；
- 两种输出形状：`envelope`（`{content, calls}`）与 `action`（`{name, arguments}`）。

### 3.6 结果回调时序

成功与失败的结果回调都发生在**写响应体之前**；被取消的请求不记录结果。这样面板上的状态不会出现「先显示结果、后补上错误」的错序。

## 4. 模型配置合并写入

### 4.1 目标与归属

写入目标由 `targets.rs` 统一定义（`Target::ALL`）：**所有已检测到的插件**——WorkBuddy 与 CodeBuddy（v1.0.4 起）。各目标的 `models.json` 路径解析见 `workbuddy_config.rs` / `codebuddy_config.rs`（两者逐行对照，解析失败**不会**回退到猜测路径——宁可报错也不写错文件）；「已安装」的唯一判据是定位成功，未检测到的目标在 `sync.targets` 里报 `missing` 并说明原因，不影响其他目标写入。

每个由本应用写入的条目都带归属字段：

```json
{ "buddyBridgeOwner": "buddy-bridge-v1" }
```

`OWNER = "buddy-bridge-v1"`。合并规则：

- **新增 / 更新**自己名下的条目；
- **清理**自己名下但本轮不再发布的条目；
- 用户手动配置的条目、以及对象里的其他元数据**原样保留**（只增删改自己的键）。

### 4.2 四重安全机制

| 机制 | 作用 |
|---|---|
| **文件锁** | 防止并发刷新互相踩踏；锁超过 **5 分钟**（`LOCK_STALE_MS`）视为上次同步已崩溃，允许抢占 |
| **二次读取** | 写入前重读一次，若发现文件在本次同步期间被改动，放弃并报 `WorkBuddy configuration changed during sync; retry refresh` |
| **存量备份清扫** | 本工具**不再写新备份**（备份从来没有读取方，却按发布次数在插件配置目录里堆积）；每次同步——包括内容没变的那次——都按同名族白名单 `<配置文件名>.buddy-bridge-<纯 ASCII 数字>.bak` 删掉旧版本攒下的存量备份，用户自己命名的 `*.bak` 与任何其它文件一律不碰 |
| **原子替换** | `rename` 遇 `EPERM` / `EACCES` / `EBUSY` 时退避重试（最长约 1.5 秒） |

### 4.3 无变化判定与拒绝写入

- 合并结果与磁盘内容一致时**不重复写盘**，返回 `changed: false` 与 `count`——界面据此显示「配置已是最新，共 N 个模型，无需重复写入。」；
- 目标文件不是可识别的 WorkBuddy 配置时，报 `Unrecognized WorkBuddy models.json; left unchanged`，**文件保持不动**；
- 模型列表为空时默认拒绝写入（`allow_empty` 为假），避免把用户配置清空——**探测 / 读取失败、面板「导入」这类路径都走这一侧**；只有**用户意图的清空**才显式传 `allow_empty = true`，实读共三处：启动时上一轮结果不可沿用（先摘掉旧发布再走完整导入）、**关停**（`shutdown` 传 `Some(Vec::new())`，见下）、以及 WorkBuddy 配置文件路径变更（换文件时清掉旧文件名下的条目）。
- 需要目标已存在时（`require_existing`）会先校验，避免误新建一个空配置。
- **插件目录已在、只是 `models.json` 不在时按空配置补建**（`workbuddy_config::ensure_models_file`，CodeBuddy 有同款对称实现）：内容写成 `[]`（`EMPTY_MODELS_FILE_TEXT`），让「装了插件但从未保存过自定义模型」的机器不再被永久判为「未检测到」。三道闸门：文件已存在**绝不改写**；父目录不存在**不替插件建目录**（目录不在＝没装，凭空建出来会造出「已安装」的假象）；任何 IO 失败静默返回 `false`，检测链照旧报未检测到。**只有默认发现位置参与补建**，环境变量或导入动作显式指定的位置一律不补——那里失效必须照旧报错。🔴 补建出来的文件能否被插件自身读入**未实机验证**（按既有语义写成数组形态，插件若只认 `{"models":[]}` 对象形态可能读不出；文件原本不存在，无从得知插件偏好）。
- ⚠ 自 2026-10-10 起写路径**完全不产生备份**：配置被本工具写坏时**没有自动回滚点**，唯一兜底就是上表那道原子替换（旧版安装包仍在写备份，升级到当前版本才停止）。

落盘文本与 `JSON.stringify(merged, null, 2) + "\n"` **逐字节一致**（先做 JS 数字规范化再缩进），因此用编辑器、Git 或 diff 工具对比时不会出现无意义噪声。
